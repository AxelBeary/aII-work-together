## 3 逐条卡片

> 每条：**看到什么** → **对我们有用的一句** → 证据强度。链接均于 2026-10-23 访问。

**C01 · Codex 开发者命令总表（官方）**
`codex resume` 的 `SESSION_ID` 类型原文是 `uuid | session name`；`codex exec resume [SESSION_ID]` 支持 `--last`／`--all`；`codex queue --thread <SESSION_ID> --message "..."` 一段原文是「Queue a text message for an existing session」。
→ **`codex queue` 是 CLI 层面唯一一条「往已有会话投一条消息」的命令**，且它接受 UUID 或精确会话名。
强度：强。〔R1〕

**C02 · Codex app-server 协议（官方 + 源码 README）**
`thread/list` 支持 cursor 分页与 `cwd`／`sourceKinds`／`archived`／`searchTerm`／`sortKey` 过滤，返回带 `status{type}`（`notLoaded`/`idle`/`systemError`/`active`）；`turn/steer` 原文「add user input to an already in-flight regular turn without starting a new turn」，必须带 `expectedTurnId`，不匹配就报 `invalid request`；`thread/inject_items` 原文「append raw Responses API items to a loaded thread's model-visible history without starting a user turn」；`thread/loaded/list` 返回**当前在内存里的** thread id。
→ 「在跑」是**可查询的一等状态**（`active` + `activeFlags` 如 `waitingOnApproval`），不是猜的。
强度：强。〔R2〕〔R3〕

**C03 · Codex 会话落盘布局**
每个会话一个 JSONL，追加写；`sessions/YYYY/MM/DD/rollout-<时间戳>-<uuid>.jsonl`，归档进 `archived_sessions/`；`history.jsonl` 存每条 prompt + session id；`[history] persistence = "none"` 可整体关掉；`codex exec --ephemeral` 单次不落盘。
→ 想「不问对方就列出本机会话」，codex 这条**可以直接扫盘**：文件名尾部就是可续跑的 id。
强度：目录与语义 强；`YYYY/MM/DD` 精确层级 中（官方只写「JSONL 存在 sessions 下」，层级来自实测文）。〔R3〕〔R4〕

**C04 · Claude Code 会话管理（官方）**
transcript 落在 `~/.claude/projects/<project>/<session-id>.jsonl`，`<project>` 是工作目录把非字母数字换成 `-`；**官方明说这份格式是内部的、会随版本变，「脚本直接解析会坏」**，要程序化就用 `/export` 或脚本接口；保留期 `cleanupPeriodDays` 默认 30 天。
→ 我们自己扫盘可以，但**要按「尽力而为」定位，不能把它当契约**——这正是我们要在 `board` 里给每条发现标 `source=discovered` 的理由。
强度：强。〔R5〕

**C05 · Claude Code 跨会话消息（官方，最接近我们 `board msg` 的样本）**
每个会话绑一个 inbox socket（macOS/Linux 是 Unix domain socket，Windows 是命名管道）；路径在 `/status` 的 `Peer address` 行（前缀 `uds:`），并导出为环境变量 `CLAUDE_CODE_MESSAGING_SOCKET` 与 `CLAUDE_CODE_MESSAGING_TOKEN`；脚本可自己往 socket 投递，Windows 上**第一行必须是** `{"type":"auth","token":"<token>"}`；投递后的读取时机是「接收方在工具调用间隙」，**若对方空闲则直接起一个新回合**；接收方三态 `accept`／`hold`／`refuse`。
→ 这就是「真·注入」的产品级答案：**不是往进程里插话，而是把消息送进对方的 inbox，由对方的调度循环在安全点(工具调用间隙)取**。
强度：强。〔R6〕

**C06 · Claude Code agent view／attach（官方）**
`claude agents` 是「本机所有后台会话」的一张表，**跨项目默认全列**，`--cwd` 收窄；`claude agents --json` 是给脚本的口径（官方明确：别去读 `~/.claude/jobs/`）；`claude attach <id>` 接管；`claude --resume <正在跑的后台会话> "prompt"` 会先投递再 attach。
→ 回答我们的问题 2：「本机有哪些会话、谁的、在哪个目录」在 Claude 这边是**产品自带**的（`--json` + `--cwd`）。
强度：强。〔R7〕

**C07 · opencode CLI：`session list` 与 `run --session`**
`opencode session list` 支持 `-n/--max-count` 与 `--format table|json`；源码里 JSON 输出字段就是 `id`／`title`／`updated`／`created`／`projectId`／`directory`；`opencode run` 的 `--session`（`-s`）语义是「session id to continue」，`--fork` 需配合 `--continue`／`--session`。
→ **`directory` 字段直接回答了「这个会话属于哪个目录」**，字段比 Codex 的 CLI 还全。
强度：强（官方 CLI 文档 + 源码 `session.ts`）。〔R8〕〔R9〕

**C08 · opencode server：唯一能在「对方在跑」时塞话的公开面**
`opencode serve` 起 headless HTTP server（默认 `127.0.0.1:4096`，`OPENCODE_SERVER_PASSWORD` 可加 basic auth）；`POST /session/:id/prompt_async`「Send a message asynchronously (no wait)」返回 204；`GET /session/status` 一次拿到**所有会话**的状态；`POST /session/:id/abort` 可打断；`/tui/append-prompt`＋`/tui/submit-prompt` 可直接驱动 TUI 提交。
→ 关键判断：**opencode 的注入能力不在 CLI，在 server**。所以「能不能注入」的正确答案取决于「对方是不是跑在 server 上」。
强度：强。〔R10〕

**C09 · Gemini CLI 会话管理（官方）**
会话存 `~/.gemini/tmp/<project_hash>/chats/`；`gemini --list-sessions` 输出形如 `1. Fix bug in auth (2 days ago) [a1b2c3d4]`；`gemini --resume`／`-r` 支持 `latest`／序号／UUID，且可带新 prompt；**官方明文：会话按项目隔离，只能 resume 本项目的会话，跨项目必须先 `cd` 进去**。
→ 反面教材：它把「会话绑 cwd」做成了硬约束，跨项目连列都列不出来。
强度：强。〔R11〕

**C10 · Gemini CLI 的并发真相（PR 描述，含源码级说法）**
`/fork` 这个命令的立项理由原文：「When two terminals `--resume` the same session ID concurrently, both processes write to the same JSON file via `fs.writeFileSync()` with no locking — last write silently overwrites the other's messages, corrupting the persisted session.」
→ 这是本报告里**最值钱的一条负面证据**：续跑式投递在「同一会话被两个进程续」时会**静默损坏**，而且没有任何报错。
强度：中（PR 作者描述 + 已被合并的 `/fork` 行为；未逐行核到源码断言）。〔R12〕

**C11 · Qoder 会话管理（国际版官方）**
`~/.qoder/projects/<处理后项目名>/<session-id>.jsonl` ＋ `<session-id>/state.json`；`--session-id` 可指定固定 id「便于脚本或自动化流程引用固定会话」；`-c`／`-r <id>`／`--fork-session`／`--list-sessions`／`--delete-session <index>`（**按序号删**）；`QODER_CONFIG_DIR` 改根。
→ 「按序号删」说明它的列表是**给人看的**，序号不是稳定标识——我们要落地时⛔ 别学它。
强度：强。〔R13〕

**C12 · Qoder CN 是另一份发行版（官方）**
`docs.qoder.cn` 上同一套命令、同一套语义，但二进制是 `qodercn`、根目录是 `~/.qoder-cn`、环境变量是 `QODERCN_CONFIG_DIR`。
→ **「Qoder 到底是哪个产品」有答案了：同一产品的两个发行版，配置根不同**。所以我们在 `board` 里登记 provider 时必须把 `qoder` 与 `qodercn` 当**两个 provider**，否则会互相看不见对方的会话。
强度：强。〔R14〕

**C13 · Cursor CLI 参数（官方）**
`--resume [chatId]`「Resume a chat session」；`--continue`「Continue the previous session (alias for `--resume=-1`)」；子命令 `ls`「Resume a chat session」、`resume`、`create-chat`「Create a new empty chat and return its ID」；隐藏命令 `agent acp` 起 ACP server。
→ `create-chat` 这个设计值得抄：**先拿 id，再说话**，脚本侧就不用去解析列表。
强度：强（参数表）／注入：未确认。〔R15〕

**C14 · Cursor 会话落地位置（第三方）**
第三方整理为 `~/.cursor/chats/<projectId>/<chatId>/store.db`（projectId 是 cwd 的哈希），chatId 为 UUIDv4；同时官方口径说会话**绑账号**并跨端同步。
→ 两个口径并不矛盾（本地缓存 + 云端主存），但**我们只采信「绑账号」这条官方说法**；扫盘方案对 Cursor ⛔ 不落地。
强度：中／弱。〔R16〕

**C15 · Aider 没有会话概念（官方 options）**
`--restore-chat-history`「Restore the previous chat history messages (default: False)」；`--chat-history-file` 默认 `.aider.chat.history.md`；`--input-history-file` 默认 `.aider.input.history`。
→ Aider 只能「整份 md 全量回灌」，**连「续某一个会话」都做不到**。它证明了一件事：没有会话 ID 的架构，谈不上定向投递。
强度：强。〔R17〕

**C16 · Continue CLI 的列表字段（源码）**
`cn ls --json` 输出 `{sessions:[{id, timestamp, workspaceDirectory, title, firstUserMessage, isRemote, remoteId}]}`；会话文件 `~/.continue/sessions/<uuid>.json`，另有 `sessions.json` 索引；`--resume` 只到「最近一条」，选具体一条要走 TUI 选择器或 `--fork <id>`。
→ **`workspaceDirectory` + `firstUserMessage` + `isRemote` 三件套**，是「人一眼认出这是哪个会话」的最小可用字段集。
强度：强。〔R18〕

**C17 · Hermes Agent 的会话与「按终端」语义（官方）**
会话存 SQLite `~/.hermes/state.db`；id 形如 `20250305_091523_a1b2c3`；`hermes sessions list` 浏览；`--resume <id|标题|latest>`；`--in <dir>` 按目录取最近；**裸 `-c` 是终端感知的**——每个终端在 `~/.hermes/terminal-sessions/` 留 breadcrumb，两个 pane 各自续各自的会话。
→ 这条直接解决我们的一个真痛点：**「谁是谁的会话」可以由启动端自报并落盘，而不是靠猜**。
强度：强。〔R19〕

**C18 · Hermes gateway 的「准入」模型（官方开发者文档）**
经典 gateway 客户端原文：会打印 `Session:` id；输入以**新的 `input_id`** 被接纳（admitted）；`/stop` 是「execution-generation-fenced interrupt」；有 `/approve ID once|deny`、`/answer ID TEXT`、`/discard ID`（承认一次跨 owner 重启丢失的 admission）。
→ 这是「常驻服务式」的完整语义：**注入不是 send，是 admit**，且必须能表达「这条 admission 丢了」。
强度：中-强（文档明确，但未给 RPC 名称）。〔R20〕

**C19 · mcp_agent_mail：邮件模型的边界**
`send_message` 写 Git 存档 + SQLite 索引 + 每位收件人一份 inbox 副本；`fetch_inbox` 取；`acknowledge_message` 确认；`fetch_inbox_events` 是「durable, recipient-scoped delivery feed for monitors」；另有 advisory 文件租约与 pre-commit 守卫。
→ 它把「投递」与「已读」分成了三件事：**存在／送达／确认**，而且明确说 monitor 用事件流、人用 inbox。我们现在的 `board msg` 只有前两件。
强度：强。〔R21〕

**C20 · coder/agentapi：PTY 注入的代价（已弃）**
`agentapi server -- claude` 起 HTTP 服务；四端点 `POST /message`／`GET /messages`／`GET /status`／`GET /events`；原理原文「runs an in-memory terminal emulator… translates API calls into appropriate terminal keystrokes and parses the agent's outputs into individual messages」，靠**屏幕快照差分**切消息。
→ 结论：能注入，但**靠截屏**。README 顶部已明写 deprecated。
强度：强。〔R22〕

**C21 · agent-http：同一 API 形状，但走原生 channel**
自述「Unlike agentapi… uses Claude Code's native channel system. Messages are exact — no terminal diffing, no TUI artifact stripping」；API 与 agentapi 兼容（`POST /message` 等）。
→ 佐证 C05：**正路是原生 channel／socket，不是截屏**。
强度：中（作者自述）。〔R23〕

**C22 · Kangentic 的十四引擎对照表（第三方编排器）**
逐引擎列了 resume 命令与「Handoff Source」（能不能读对方原生历史）：Codex `codex resume <id>` + 解析 `~/.codex/sessions/.../rollout-*.jsonl`；Gemini `--resume <id>` + 解析 `~/.gemini/tmp/<…>/chats/session-*.jsonl`；opencode `ses_*` + 插件钩子 `session.idle`；Cursor `cursor-agent --resume="<id>"`，id 取自 `--output-format stream-json` 的 init 事件；**Aider 明确「No session resume」**；另有全局并发上限 `agent.maxConcurrentSessions` 默认 8、超了排队。
→ 三件事值得抄：① **会话 id 从「结构化输出流」里取，不从列表里刮**；② **读对方原生历史文件做 handoff，而不是让上家写摘要**；③ 并发上限是**全局池**不是每项目。
强度：中（工程方文档，未开源码）。〔R24〕

## 4 「指定会话投递」到底有几种真做法

把 22 条证据压成三类。**判断标准：消息到达时，对方的进程是"活的"还是"新的"。**

### A 续跑式（resume-and-replay）——「叫醒」，不是「插话」

- 做法：拿 sessionID 起一个**新进程**，把历史读回来，再问一次。
- 谁这么做：`codex exec resume`／`claude -p --resume`／`opencode run -s`／`gemini -r`／`qoder -r`／`hermes -r`／`cn --resume`。**我们现在的 `board msg wake` 就是这一类。**
- 代价（四条，都有出处）：
  1. **不能插话**：对方在跑时你没有入口（Gemini/Codex/Qoder 的 CLI 都没有；Claude 是例外，见 B）。
  2. **历史要重放**：每次唤醒都是全量 context 重建 ⇒ 成本随会话变长而涨，且绕不过 prompt cache。
  3. **同会话并发会坏**：Gemini 是**静默覆盖**（C10）；Claude 是**交错写入**（C05）。
  4. **醒来的是"一个新执行者"**：它没有原进程的内存态（未落盘的中间变量、正在跑的工具）——只能从磁盘重建。
- 什么时候够用：**对方已经退出**。这是我们的主场景，所以这条路不能丢。

### B 消息总线式（store-and-poll）——「投进信箱」

- 做法：消息落库／落文件，**由收件方自己来取**；取的时刻由收件方决定。
- 谁这么做：`mcp_agent_mail`（`fetch_inbox` + `acknowledge_message`）、**我们现在的 `board msg inbox`**、Continue 的远端会话列表（弱）。
- 代价：
  1. **延迟不可控**：对方不 poll 就永远不到；要"叫醒"必须叠加 A 或 C。
  2. 但**它是最稳的一层**：无进程、无端口、无锁，天然跨机、天然审计、天然"存住"。
- 关键洞察（来自 C19）：总线要分三态才有用——**STORED（存住）／DELIVERED（送达对方进程）／ACKED（对方承认读到）**。混成一个"已发送"，就是我们踩过的「把存住说成送到」。

### C 常驻服务式（daemon / app-server）——**唯一能真注入的一类**

- 做法：会话被一个**长期进程**持有（server／supervisor／gateway），客户端只发 RPC；服务端在**安全点**把消息插进正在进行的回合，或起下一回合。
- 四种实现样本：
  | 实现 | 注入原语 | 安全点语义 |
  |---|---|---|
  | Codex app-server | `turn/steer`（带 `expectedTurnId`）、`turn/start`、`thread/inject_items` | 回合中；`expectedTurnId` 不匹配即拒绝 |
  | opencode server | `POST /session/:id/prompt_async`、`/tui/submit-prompt` | 异步入队，204 即返回 |
  | Claude Code | per-session socket ＋ `SendMessage`／`ListAgents`；`claude attach` 后命令行的 prompt 也算 | **工具调用间隙**；空闲则起新回合；`accept`/`hold`/`refuse` 三态 |
  | Hermes gateway | `input_id` admission ＋ `/answer`／`/approve`／`/discard` | 准入 + 代次围栏，能表达「这条丢了」 |
- 代价（四条）：
  1. **要有常驻进程**：谁拉起、谁保活、崩溃后谁恢复——这是新增的一整块运维面。
  2. **端口／管道 = 新的攻击面**：Codex 的 ws 监听默认**允许未认证连接**（官方原文警告），Claude 的 socket 在 Windows 上**强制**首行 auth token——两种截然不同的默认值，得自己选。
  3. **必须服务端串行化**：客户端自己加锁没用（见 E-34 类事故）。
  4. **能力不是对称的**：只有跑在 server 上的会话可注入，跑在裸 CLI 上的不行 ⇒ 我们的投递能力表必须是「按 provider + 按运行形态」两维，不能只按 provider。

### D（附）终端仿真式——**别做**

`agentapi` 那套「PTY + 屏幕差分」。能注入，但脆弱、已弃、无法判断"已读"。列出来只为解释**为什么 Claude 要做 socket 而不是截屏**（C21）。

**一句话结论**：**"往指定会话投递"只有两条真路——A 叫醒一个已退出的执行者，C 把话塞进活着的调度循环。B 不是投递，是排队。** 我们现在的 `board msg` 是 B + A 手工拼接，缺的正是 C 那一格。

## 5 五条能直接搬进 `board msg` 的做法

> 每条：改哪个文件／哪张表 → 具体做法 → 防的是什么事故。

### 5.1 把投递做成**能力矩阵**，而不是一条 `wake` 命令

- 改：`tools/messages.py`（新增 `PROVIDER_CAPS` 常量表 + `deliver()` 分派）、`tools/cli.py`（`board msg send/deliver` 加 `--via {auto,store,resume,inject}`）。
- 内容：provider × 运行形态 → 可用原语。
  - `codex` → `codex queue --thread <id> --message` / app-server `turn/steer` / `codex exec resume`
  - `claude` → socket 投递（`CLAUDE_CODE_MESSAGING_SOCKET`）/ `claude --resume <id> "…"`（**仅后台会话**）/ `claude -p --resume`
  - `opencode` → `POST /session/:id/prompt_async`（有 server 时）/ `opencode run --session`
  - `gemini`／`qoder`／`qodercn`／`hermes`／`cn` → 只有 resume
  - `aider` → **不支持定向投递**（无 session id），只能落 store 等人读
- 防的事故：把「能 resume」当成「能注入」，在对方正在跑的时候又起一个进程去抢同一个会话（Gemini 会**静默写坏**，见 C10）。

### 5.2 新增**会话发现**（问盘不问人）

- 改：新增 `tools/sessions.py`（只读扫描 + 归一化），`tools/storage.py`（新表 `sessions`）。
- 表结构建议：`sessions(session_id TEXT, provider TEXT, cwd TEXT, title TEXT, updated_at INTEGER, origin TEXT, owner_seat TEXT, source TEXT, PRIMARY KEY(provider, session_id))`；`source` 取 `discovered|self-reported`，`origin` 取 `cli|exec|server|background`。
- 扫描目标（**全部只读**，逐 provider 一个适配函数）：
  - `codex`：`$CODEX_HOME/sessions/**/rollout-*.jsonl`（文件名尾部＝可续跑 id）
  - `claude`：`~/.claude/projects/*/*.jsonl`（`<project>` 目录名反推 cwd；**标明是"尽力而为"，别当契约**，见 C04）
  - `opencode`：先 `opencode debug paths db` 取路径，再对 SQLite 做只读查询（`id/title/directory/time_updated`）
  - `gemini`：`~/.gemini/tmp/*/chats/*.jsonl`（外加 `projects.json` 反查路径）
  - `qoder`／`qodercn`：`~/.qoder/projects/*/*.jsonl`、`~/.qoder-cn/projects/*/*.jsonl`
  - `hermes`：`~/.hermes/state.db`
  - `cursor`：**不扫**（会话绑账号，本地布局无官方口径，见 C14）
- 防的事故：现在「本机有哪些会话、谁的、在哪个目录」只能靠对方自报 ⇒ 对方没报就等于不存在；且**自报与真实会不一致**。

### 5.3 会话级租约：续跑前先抢锁

- 改：`tools/storage.py`（新表 `session_leases(session_id TEXT PRIMARY KEY, provider TEXT, seat TEXT, pid INTEGER, at_mono REAL, hb_mono REAL)` + `lease_log` 复用）、`tools/messages.py`（`wake` 前置 `guard_session_holder()`）。
- 语义照抄现有卡片租约（`leases.card_id` 主键 + 心跳 + `guard_holder`）：**同一 (provider, session_id) 同一时刻只许一个续跑者**；TTL/心跳用单调时钟（我们已有 `at_mono` 的教训 E-37）。
- 防的事故：两个席位同时 `wake` 同一个会话 ⇒ Gemini 静默覆盖、Claude 交错写入（C05／C10）。这是**数据损坏级**事故，不是「慢一点」。

### 5.4 投递状态三态化 + 不重发守卫升级

- 改：`tools/storage.py`（`messages` 表加 `delivery_state TEXT`、`delivered_at INTEGER`、`attempts INTEGER`、`last_error TEXT`；新表 `msg_deliveries(msg_id, attempt, via, state, at, detail)`）、`tools/messages.py`。
- 状态机（严格单向，⛔ 不许回退）：
  - `STORED` — 落库，对方还不知道（＝现在的全部行为）
  - `DELIVERED` — **对方进程确认收到**（codex `queue` 返回、opencode `204`、claude socket 写成功）
  - `ACKED` — 对方**回了消息**（复用现有 `msg_reads` 的 ack 语义）
  - `HELD` — 有通道但被拒／超时（保留现有退出码 2 的语义）
- 防的事故：把「命令没报错」当「送到了」——官方文档里 Codex 的 `queue`／opencode 的 `prompt_async` 都只承诺**入队**，不承诺被模型读到。

### 5.5 会话所有权 = **启动端自报 + 终端/进程绑定**

- 改：`tools/board.py`（新建会话时写一条 `sessions` 记录）、`tools/messages.py`（派工时把 `--session` 一并落库）、`tools/server.py`（`/api/sessions` 只读端点给 UI）。
- 做法（抄 Hermes 的 breadcrumb 思路，C17）：**谁起的会话谁登记**——provider、session_id、cwd、seat、pid、启动时刻，写进 `sessions` 表；`-c`／「最近一条」这类模糊语义一律**按 seat 或 pid 解析**，⛔ 不用「全局最近」。
- 防的事故：`-c`／`--continue` 这类「最近一条」在多席位并行时**必然抢错**（Hermes 为此专门做了 terminal-sessions breadcrumb）；我们如果照抄 `-c` 语义而不抄 breadcrumb，等于把事故写进接口。

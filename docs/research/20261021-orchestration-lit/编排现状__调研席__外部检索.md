## 2 一页地图

### A 任务/状态模型

- **共识**：所有严肃框架都把「做到哪了」表达成**持久化的状态快照 + 一个可恢复的指针**（LangGraph `thread_id`+`checkpoint_id`；Temporal Workflow Id+Event History；CrewAI `state.id`+`@persist`；OpenAI `session_id`+`RunState`）。「谁在做」几乎都不进状态机，而是交给**运行时/租约层**（AutoGen 的 Agent ID 由 runtime 管；K8s 的 Lease 管 holder）。
- **有争议**：状态粒度。LangGraph 细到**每个 node 的 pending write**（`checkpoint_writes` 表，可按 task 恢复不重跑）；Temporal 细到**每条 Event**；Airflow/Dagster 只到**任务实例级**。粒度越细，恢复越省，但写入放大越严重——LangGraph 自己都出了 `DeltaChannel`（beta）来压 checkpoint 体积。
- **空白**：**没有一个框架把「失败」和「取消中」当一等状态**做到卡片级。Airflow 有 `up_for_retry` 但那是 DAG 任务；Dagster 有 `CANCELING` 但那是 run。**「因上游失败而停」只有一个实现**（Airflow `upstream_failed`）。Agent 框架（LangGraph/OpenAI/CrewAI/Claude SDK）**完全没有**「上游失败」概念——它们假设图是静态的。

### B 租约 / 幂等 / 续跑

- **共识**：**at-least-once + 幂等键**是工业界标准答案，没有例外。AWS 用调用方提供的 `ClientToken` 做去重键，且要求「记 token + 全部变更」在一个 ACID 事务里；Temporal 用 Workflow Id 保证同一时刻只有一个 open execution；SQS 用 visibility timeout + 心跳续租，并明说 at-least-once **不保证不重复投递**。
- **有争议**：**租约够不够**。K8s 的 Lease 只解决「谁以为自己是 holder」；Kleppmann 2016 指出：进程暂停/网络延迟会让**两个客户端同时以为自己持锁**，唯一解法是 fencing token——单调递增，且**存储端必须主动拒绝旧 token 的写**。这一点在 agent 框架里**基本没人做**。
- **空白**：任务书里假设存在的「LLM agent 的 exactly-once 是幻想，应做 at-least-once + 幂等落盘」这句话，**我没找到任何一手来源这么写**（§7 第 1 条）。现有资料只到「at most once 靠 idempotency key」这一步，**没有**针对「一次 agent 调用 10 分钟、会产生文件副作用、重试付双倍钱」这个具体场景的成文结论。这是个真空。

### C 人机协同闸

- **共识**：闸门放在**工具调用前**（LangGraph 在 `@tool` 里 `interrupt()`；OpenAI 用 `needs_approval` 拦 tool call），**不是**提交后；审批载荷最小集是**「工具名 + 参数」**（OpenAI `ToolApprovalItem` 的 `tool_name`/`arguments`/`agent.name`）。**恢复时节点会从头重跑**，所以 `interrupt()` 之前的副作用必须幂等（LangGraph 文档明写）。
- **有争议**：闸门该有几个。HumanLayer 主张在**设计文档**阶段就拦（「catch mistakes before 2,000 lines of code」），而不是等代码 diff；LangGraph/OpenAI 只提供**机制**，把「放几个闸」留给应用。另一种争议是「粘性批准」——OpenAI 的 `always_approve` 会让后续同类调用不再问，且 **shell/apply_patch 的粘性决策不按 agent 隔离**（官方明确警告）。
- **空白**：**「审批疲劳／橡皮图章」在 agent 场景下没有实证**。最接近的是 Buçinca 2021（N=199）：**加解释并不能减少 overreliance，有些情况下还加重**；能减少的是「认知强制动作」（逼人多想一步），但**最有效的设计最不受欢迎**。这篇不是 agent 审批实验，只能算旁证（§7 第 2 条）。

### D 可观测与追责

- **共识**：trace 的最小追责单元是**一次逻辑操作的全部重试**（OTel 原文：span SHOULD cover the duration of the logical operation **with all retries**），字段固定为「模型 + token + 工具 + 错误类型」：`gen_ai.operation.name` / `gen_ai.provider.name` / `gen_ai.request.model` / `gen_ai.response.model` / `gen_ai.usage.input_tokens` / `gen_ai.usage.output_tokens` / `gen_ai.response.finish_reasons` / `error.type`。会话维度用 `gen_ai.conversation.id`，agent 维度用 `gen_ai.agent.id`/`name`/`version`。
- **有争议**：trace 与「业务台账」是否同一份数据。Langfuse 把 trace 属性**下沉复制到每条 observation**（查询快、写入放大）；AgentOps 把 session 当一等对象（`End State`/`End State Reason`）；Phoenix 用 span kind 分类（`Guardrail`/`Evaluator` 都是独立 kind）。
- **空白**：**「谁批准的」在 GenAI semconv 里没有字段**。`gen_ai.*` 覆盖了模型、token、工具、会话，但**没有 approver 身份、没有审批动作、没有证据等级**。也就是说：OTel 能告诉你「调了什么」，**不能告诉你「谁放行的」**。我们的 `journal.jsonl` 在这一点上比 semconv 全。

### E 已知失败模式

- **共识**：多 agent 的收益主要来自**并行读 + 摊开 token**（Anthropic：token 用量单独解释 BrowseComp 80% 的方差；多 agent 比 chat 多烧约 15× token）。**写操作并行会因「隐式决策冲突」而崩**（Cognition：两个 subagent 各自做了未声明的假设，合起来风格不一致）。MAST 给了硬数字：7 个开源 MAS 的失败率 **41%–86.7%**，14 种失败模式，κ=0.88。
- **有争议**：多 agent 到底该不该建。Anthropic 说「breadth-first 检索类值得」；Cognition 说「默认别建，单线程线性 agent 能走很远」；LangChain 的调停最有用：**读型多 agent 容易，写型多 agent 难**——因为读可以并行，写要合并。
- **空白**：**没有统一的「什么时候不该用多 agent」判据表**，只有三条互补的经验法则（并行读 / 上下文超窗 / 值钱到能付 15× token）。**角色串味（role bleed）在 MAST 里有名字**（FM-1.2 Disobey role specification），但**没有量化研究**说它在什么条件下发生得多。

#### A1 · Persistence（LangGraph 持久化）
- **作者/机构**：LangChain（官方文档）
- **年份**：2026（抓取日；页面未标发布日）
- **链接**：https://docs.langchain.com/oss/python/langgraph/persistence
- **一句话结论**：持久化被拆成两层——checkpointer 存「单线程图状态快照」，store 存「跨线程 KV」，两者用途不同不能互相替代。
- **方法**：官方概念文档 + 代码样例（非实测）。
- **可抄**：`durability` 三档 **`"exit"` / `"async"` / `"sync"`**（`exit`＝只在退出/中断时落盘，`sync`＝每步前同步落盘）。这正好对应我们「心跳/事件/交付物」三种不同重要度的写。
- **证据强度**：强（字段名为原文）。

#### A2 · Checkpointers（状态快照的字段全集）
- **作者/机构**：LangChain
- **年份**：2026
- **链接**：https://docs.langchain.com/oss/python/langgraph/checkpointers
- **一句话结论**：状态快照 `StateSnapshot` 有固定七字段，其中 `next=()` 表示「图已完成」，`parent_config` 构成可回溯链。
- **方法**：官方字段表 + SQL schema 原文。
- **可抄**（原文照录）：
  - `StateSnapshot` 字段：`values` / `next` / `config`（含 `thread_id`、`checkpoint_ns`、`checkpoint_id`）/ `metadata`（含 `source`: `"input"|"loop"|"update"`、`writes`、`step`）/ `created_at` / `parent_config` / `tasks`（`PregelTask`：`id`、`name`、`error`、`interrupts`、可选 `state`）。
  - 表结构：`checkpoints(thread_id, checkpoint_ns, checkpoint_id, parent_checkpoint_id, type, checkpoint, metadata)` + `writes(thread_id, checkpoint_ns, checkpoint_id, task_id, task_path, idx, channel, type, value)`。
  - 关键机制「pending writes」：同一 super-step 里成功的 node 先落 `writes`，失败的 node 不重跑。
- **证据强度**：强。

#### A3 · Interrupts（人工中断的语义与坑）
- **作者/机构**：LangChain
- **年份**：2026
- **链接**：https://docs.langchain.com/oss/python/langgraph/interrupts
- **一句话结论**：`interrupt()` 用抛异常实现暂停，**恢复时整个 node 从头重跑**，所以 `interrupt()` 之前的副作用必须幂等。
- **方法**：官方文档 + 大量反例代码。
- **可抄**：
  - `interrupt(payload, response_schema=...)`；恢复用 `Command(resume=...)`；载荷出现在 `stream.interrupts`（旧 API 是 `result["__interrupt__"]`）。
  - 多中断并发时按 **`Interrupt.id` → resume value** 映射恢复。
  - 硬规则（原文）：`interrupt` 不能被 bare `try/except` 包；同 node 内**不能条件跳过 interrupt**（匹配是 index-based）；`interrupt` 前的事务要幂等（用 upsert，不用 create+append）。
  - 静态断点：`interrupt_before=["node_a"]` / `interrupt_after=[...]`，明确注明「**不推荐**用于人机协同」。
- **证据强度**：强。

#### A4 · Flows（CrewAI 的事件驱动流程）
- **作者/机构**：CrewAI
- **年份**：2026
- **链接**：https://docs.crewai.com/en/concepts/flows
- **一句话结论**：用 `@start`/`@listen`/`@router` 做事件驱动，state 自动带 UUID，`@persist` 默认落 SQLite，且**区分 resume 与 fork**。
- **方法**：官方文档。
- **可抄**：
  - `@persist` 默认后端 **`SQLiteFlowPersistence`**；`kickoff(inputs={"id": <uuid>})`＝**resume**（同一 `flow_uuid` 续写历史）；`kickoff(restore_from_state_id=<uuid>)`＝**fork**（新 `state.id`，源历史不动）。
  - `@human_feedback(message=..., emit=["approved","rejected","needs_revision"], default_outcome="needs_revision")`——**三态 + 默认走向**，超时/无人理时有明确落点。
  - 计量字段（`UsageMetrics`）：`total_tokens` / `prompt_tokens` / `completion_tokens` / `cached_prompt_tokens` / `cache_creation_tokens` / `reasoning_tokens` / `successful_requests`；并明确 `cached_*` **不叠加**在 `total_tokens` 之上。
- **证据强度**：强。

#### A6 · Agent Identity and Lifecycle（Agent ID 的两段式）
- **作者/机构**：Microsoft

#### A8 · Human-in-the-loop（RunState 的可序列化暂停）
- **作者/机构**：OpenAI
- **年份**：2026
- **链接**：https://openai.github.io/openai-agents-python/human_in_the_loop/
- **一句话结论**：审批是「run 级中断 + 可序列化 RunState」，暂停可跨进程恢复；但审批快照**不做身份认证**，服务端必须自己补四步。
- **方法**：官方文档。
- **可抄**（这批字段最值钱）：
  - `@tool(needs_approval=True)` 或 `needs_approval=<async callable>`；callable **fail closed**（参数缺失/空/非 JSON object/含 `NaN` → 一律转人工）。
  - 中断项 `ToolApprovalItem` 的字段：**`agent.name`、`tool_name`、`arguments`**。
  - `result.to_state()` → `state.approve(item, always_approve=...)` / `state.reject(item, rejection_message=...)` → `Runner.run(agent, state)`。
  - 服务端审批四步（原文）：① 认证 reviewer（**不得从请求体取身份**）② 授权该 reviewer 能操作该 run ③ 用服务端快照校验 decision id ④ **原子 owner-checked transition**，防重复 resume。
  - `RunState.to_json()` / `from_json()`；需与「agent 定义版本号」一起存，否则旧审批打到新代码上。
- **证据强度**：强。

#### A9 · Work with sessions（Claude Agent SDK 的 continue / resume / fork）
- **作者/机构**：Anthropic
- **年份**：2026
- **链接**：https://code.claude.com/docs/en/agent-sdk/sessions
- **一句话结论**：会话持久化**只持久化对话，不持久化文件系统**；要还原文件必须另开 file checkpointing。
- **方法**：官方文档。
- **可抄**：

- **证据强度**：强。

  - **FC2 agent 间失配**：`FM-2.1` Conversation reset｜`FM-2.2` Fail to ask for clarification｜`FM-2.3` Task derailment｜`FM-2.4` Information withholding｜`FM-2.5` Ignored other agent's input｜`FM-2.6` Reasoning-action mismatch
  - **FC3 任务验证**：`FM-3.1` Premature termination｜`FM-3.2` **No or incomplete verification**｜`FM-3.3` Incorrect verification
- **证据强度**：强（有数据集、有 κ、有公开仓；但样本是 7 个开源框架，外推需谨慎）。

#### E4 · How and when to build multi-agent systems
- **作者/机构**：Harrison Chase / LangChain
- **年份**：2025-06-16
- **链接**：https://blog.langchain.com/how-and-when-to-build-multi-agent-systems/
- **一句话结论**：E1 与 E2 看似对立其实同向；真正的分水岭是**读型 vs 写型**——「Multi-agent systems that primarily "read" are easier than those that "write"」。
- **方法**：对比两篇原文 + 引用关键段。
- **可抄**：写操作并行的双重成本＝「上下文传递」+「输出合并」；Anthropic 的**写作部分刻意由单个主 agent 一次完成**，只有检索是多 agent。

#### E5 · Context Rot
- **作者/机构**：Kelly Hong、Anton Troynikov、Jeff Huber / Chroma
- **年份**：2025-07-14
- **链接**：https://research.trychroma.com/context-rot
- **一句话结论**：18 个模型的性能随输入变长**非均匀退化**；干扰项（distractor）越多越糟；**结构连贯的长文本比打乱的长文本更伤性能**（反直觉）。
- **方法**：控制变量（固定任务难度、只变输入长度）；8 种长度 × 11 个位置；LongMemEval 子集 306 条、平均约 113k token，对比「只给相关片段」约 300 token 的 focused 版本。
- **可抄**：**同上任务，focused（~300 token）显著优于 full（~113k token）**——直接支持「派工单必须短、长材料走文件引用」。
- **证据强度**：强（有代码仓、有量）；但只测检索/复述类任务。

#### E6 · Building effective agents
- **作者/机构**：Erik Schluntz、Barry Zhang / Anthropic
- **年份**：2024-12-19（页面已标注「工具生态已变」）
- **链接**：https://www.anthropic.com/engineering/building-effective-agents
- **一句话结论**：先把问题做成**工作流**（预定义代码路径），只有「步骤数不可预测」时才升级成 **agent**；框架的抽象层会遮住 prompt，反而难调。

> ⚠️ 读法：这张表**只比「概念」不比「名字」**。Temporal 没有「卡片状态」这个概念（它管的是 workflow execution），硬填会失真，所以空格写「无」而不是编一个名字。每一格都能在 §3 对应卡片里找到原文。

### 4.1 主链路

| 概念 | 我们（`tools/board.py` `STATES`） | LangGraph | CrewAI Flows | OpenAI Agents SDK | Temporal | Airflow | Dagster |
|---|---|---|---|---|---|---|---|
| 未开始 | `待认领` | `metadata.source="input"` + `next=("node",)` | 无枚举，`state.id` 生成即开跑 | 无枚举，`RunState` 未建即不存在 | 无状态名（用 Workflow Id 唯一性表达） | `none` / `scheduled` / `queued` | `NOT_STARTED` / `QUEUED` |

| 完成 | `完成` | `next=()`（空元组） | 最后一个 `@listen` 返回 | 无 interruptions 即结束 | Workflow 进入 Closed | `success` | `SUCCESS` |

### 4.2 异常 / 人工 / 终态

| 概念 | 我们 | LangGraph | CrewAI | OpenAI | Temporal | Airflow | Dagster |
|---|---|---|---|---|---|---|---|
| 暂停/阻塞 | `阻塞`（带 `blocked_reason`） | `interrupt()` 挂起（无限等） | 无（`@human_feedback` 是等人，不是阻塞） | `RunState` 暂停 | **Workflow Pause** | `deferred` | `SUSPENDED` |
| 待人工审批 | `拍板中` | `stream.interrupts` / `result["__interrupt__"]` + `response_schema` | `@human_feedback(emit=[...], default_outcome=...)` | `ToolApprovalItem`（`agent.name`/`tool_name`/`arguments`） | Signal `approve`（官方示例） | `awaiting_input` | 无 |

| 失败终态 | **无**（失败落 `待返工`，可再改） | `PregelTask.error`（任务级，非卡级） | 无 | 异常上抛（非状态） | Workflow 失败（Closed） | `failed` | `FAILURE` |

### 4.3 我们缺什么 / 多什么

**缺（可补，按价值排序）**
1. **失败终态**：现在失败只能进 `待返工`，与「还在改」和「改不动了」无法区分。Airflow 的 `failed` + `up_for_retry` 是正确拆分。
2. **`取消中`**：我们 `已取消` 是直接终态，但真取消一个正在跑的 agent 是有中间过程的（Dagster `CANCELING` 就是为这个存在的）。
3. **`因上游失败`**：`blocked_by` 现在是「跳过」，不落「为什么没做」。Airflow `upstream_failed` 是唯一现成命名。
4. **`重试中`**：我们重试是隐式的，审计时看不出「这张卡试过 3 次」。
5. **`需要修改`（不等于打回）**：CrewAI 的 `needs_revision` 比我们的二选一（完成/待返工）细。

**多（别抄丢的）**
- **人可写的 `blocked_reason`**：上面 6 个框架**没有一个**把「为什么卡住」做成卡片字段（Airflow 只有 `upstream_failed` 这个原因名，没有自由文本）。
- **`evidence_tier`（VERIFIED / AUDITED-UNGROUNDED）**：所有框架的审批都只记 `approved: bool`，**没有证据等级**。
- **`epoch` 单调计数**：`leases` 表已经在 claim 时 +1（见 §6 第 1 条），K8s 之外很少有框架自带这个。

## 6 五条可直接搬 + 三条我们已做得更好

### 6.1 五条可直接搬

#### ① 把 `epoch` 从「记录」升级成「栅栏」（fencing token）
- **改哪里**：`tools/storage.py` 的 `touch_lease()` / `release_lease()` / `save_card()`；`tools/board.py` 的 `heartbeat()` / `release()` / `submit` 调用链；`leases` 表（已有 `epoch INTEGER DEFAULT 0`，**不用加列**）。
- **为什么**：B4 说得最清楚——租约到期 + 进程暂停，会让两个执行者同时以为自己持锁；「检查过期时间」救不了。我们现在 `epoch` 在 `claim` 时 +1 并写进 state 和事件，但**没有任何写入路径校验它**，所以它现在只是日志字段，不是栅栏。
- **怎么做**：所有对 `leases` 的写改成 `UPDATE ... WHERE card_id=? AND seat=? AND epoch=?`，影响行数 0 即拒（die）。CLI 上 `--epoch` 可省略，省略时从库里读当前 holder 的 epoch 自查。
- **代价**：CLI 参数面变大一点；`tests/` 里租约竞态那 14 条要加「旧 epoch 写入必须被拒」的正反用例。**收益**：把「被回收的进程还在外面写」这个已知边界，从「挡不住」变成「挡得住一半」（它写不进来，但它已经产生的文件副作用仍挡不住）。

#### ② 进「拍板中」时落一份结构化的 `approval.json`，而不是一句说明
- **改哪里**：`tools/board.py` 里触发 `待验收/核验中 → 拍板中` 的那条边；产出文件放卡片目录（与 `run.log`、`journal.jsonl` 同级）；`ui.html` 的拍板面板读它渲染。
- **为什么**：A8 的审批项只有三个字段（`agent.name` / `tool_name` / `arguments`），但**有结构**；我们的「拍板中」现在只有自由文本，人要看懂全靠现场解释。
- **字段建议**（照 A8 + D4 拼）：`action`（要做什么，对应 `tool_name`）、`arguments`（具体参数/文件/命令）、`actor`（哪个席位、哪个引擎/模型）、`reversible`（对应 `irreversible`）、`accept_criteria`（怎么算过）、`end_state_reason`（若拒绝，为什么）。
- **代价**：多一个文件、多一次校验（进拍板中时必须能生成，生成失败不许进）。**收益**：审批从「聊天」变成「可复核的工件」，事后追责有据。

#### ③ 状态机补三个状态：`重试中` / `因上游失败` / `失败终态`
- **改哪里**：`tools/board.py` 的 `STATES`（现 9 个）与 `TRANSITIONS` 白名单；`replay()` 的状态推导；`tests/` 里所有断言状态集合的用例。
- **为什么**：§4.2 显示这三个是**跨框架最普遍的缺口在我们这边**：Airflow 有 `up_for_retry` 与 `upstream_failed`，Dagster 有 `FAILURE`，我们一个都没有。
- **怎么做**：`失败` 作为 review 可推的终态（与 `待返工` 并存：可改的进 `待返工`，改不动的进 `失败`）；`因上游失败` 由 `blocked_by` 里任一卡进 `失败/已取消` 时自动推；`重试中` 由错误分级里的可重试分支显式落一条状态转移。
- **代价**：**中等偏大**——16 道闸里凡断言「状态全集」的都要改；老卡如果停在 `待返工`，需要一次性迁移脚本（或声明「老卡不迁移，新状态只对新卡生效」）。这是五条里唯一需要发牌席拍板的。

#### ④ 观测字段往 `gen_ai.*` 靠，但**只加事件不加列**
- **改哪里**：`tools/board.py` 的 `append_event()` 调用点（`submit` 收口、run 结束处）；事件类型新增一条 `run_summary`；**不动** `events` 表结构（`data` 是 TEXT，装 JSON）。
- **为什么**：D1 的字段名是现成的行业口径，照抄能直接被 Langfuse/Phoenix 之类消费；D1 还有一条我们没做的规矩——**span 要覆盖全部重试**，也就是一个逻辑调用记一条、里面带 `attempts`，而不是每次重试记一行。
- **字段建议**：`operation`（`chat`/`execute_tool`/`plan`…）、`provider`、`request.model`、`response.model`、`usage.input_tokens`、`usage.output_tokens`、`attempts`、`end_state_reason`（照 D4）、`host`（照 D4 的 Host Environment）。
- **代价**：事件体积变大（每卡多一条 JSON）；老卡没有这条事件，查询要能容忍缺失。**收益**：从「只有我们的界面能读」变成「任何 OTEL 生态都能读」。

#### ⑤ 高风险卡的审批加一次「认知强制动作」
- **改哪里**：`tools/cli.py` 的 `human` 子命令（进 `拍板中 → 完成` 的那条边）。
- **为什么**：C3 的实证是「加解释不减少 overreliance，强制动作才减少」；C4 又告诉我们「粘性批准」会让闸门事实上失效。两者合起来＝**默认不许一键放行**。
- **怎么做**：`human_gate != "none"` 或 `irreversible=1` 的卡，`human` 必须额外带 `--check <一句话：你核对了什么>` 或 `--reason <拒绝理由>`；低风险卡保留一键。**关键**：这个「核对」要进 `journal.jsonl`，不是只打印。
- **代价**：人手操作变慢（C3 明说最有效的设计最不受欢迎，这是已知代价）；需要一条「我就是要快」的例外开关，且例外本身要留痕。

### 6.2 三条我们已做得更好（别照抄别人把自己的优势抄没了）

#### ① 证据等级（`VERIFIED` / `AUDITED-UNGROUNDED`）是稀缺设计
- 对照：LangGraph/OpenAI/CrewAI 的审批都只落一个 `approved` 布尔；OTel 的 `gen_ai.*` **没有 approver 字段**（D1/D2 全文没有）。也就是说：**整个生态只记「发生了什么」，不记「凭什么算过」**。
- 我们的 `evidence_tier` 把「机器闸全过」和「复核席说了算」分开，直接对应 MAST 的 `FM-3.2`/`FM-3.3`。**这条不要为了对齐 semconv 而合并掉**。

#### ② 人闸是**拓扑上**绕不过的，不是一个 API 调用
- 对照：OpenAI 的 `state.approve()` 是**应用代码**调的——任何能写应用的代码都能自己 approve；CrewAI 的 `@human_feedback` 同理；Claude SDK 的 Permissions 是工具白名单，不区分「谁批的」。
- 我们是「`拍板中 → 完成` 这条边只允许 `human` actor + 人令牌哈希登记」。这是**权限位**，不是**约定**。A8 自己也承认这点：`RunState.from_json()` **不认证快照，也不认证提交者**，所以服务端必须自己补四件事——我们已经在做其中两件（身份、原子消费）。

#### ③ `阻塞` 是带原因的显式状态
- 对照：Airflow 有 `upstream_failed` 但只是「原因类别」，没有自由文本；LangGraph/OpenAI/CrewAI/Claude SDK **完全没有 blocked 概念**（它们的失败就是抛异常/抛 interrupt）；Dagster 的 `SUSPENDED` 是管理员暂停，不是执行者报障。
- 我们 `阻塞` + `blocked_reason` 让「卡在哪、为什么」是第一等数据。**补状态时别把 `阻塞` 并进 `失败`**。

## 7 未证 / 存疑清单

1. **「LLM agent 的 exactly-once 是幻想，应做 at-least-once + 幂等落盘」这句话——未取到。** 任务书假设存在这类结论；我抓了 AWS Builders' Library、Temporal（Workflow Id / message passing）、K8s Lease，**没有任何一篇这样表述**。最接近的是 AWS 的「at most once 靠 caller-provided token」与 Temporal 的「同 Id 至多一个 open execution」，二者都是**通用分布式系统**口径，**没有**针对「agent 调用 10 分钟 + 文件副作用 + 重试双倍计费」的成文论断。⇒ 这是真空，不能当成「学界共识」引用。
2. **「审批疲劳／橡皮图章」在 agent 审批场景下无实证。** 找到的只有 Buçinca 2021（N=199，AI 辅助决策，不是 agent 工具审批）。C4 的「粘性批准」是**机制证据**，不是**行为证据**——它证明闸门可被配置成失效，不证明人真的会变成橡皮图章。
3. **K8s Lease 的 `acquireTime` / `leaseTransitions` 未实证。** 我抓到的页面片段只出现 `holderIdentity`、`leaseDurationSeconds`、`renewTime`。前两个字段是我**记得存在但本次没抓到**的，所以在 B1 里只写了实证到的三个。
4. **Dagster `SUSPENDED` 的确切语义未取到。** 只拿到枚举字面量（`/api/dagster/internals`），没读到「什么操作会产生 SUSPENDED」。同理 `MANAGED`。
5. **Temporal 的「取消中」状态名未取到。** 没有抓到 cancellation 相关页面；`CANCELING` 只在 Dagster 得到实证。
6. **MAST 的 41%–86.7% 不可外推。** 样本是 7 个**开源** MAS、特定 benchmark；闭源生产系统不在样本内。引用时必须带这个限定。
7. **Anthropic 的 90.2% / 80% / 15× 不可复现。** 全部来自内部 eval 与自述分析；「token 用量解释 80% 方差」是他们的回归结论，没有公开数据集。
8. **Chroma 的结论只覆盖检索/复述类任务。** 18 个模型、LongMemEval 306 条，任务形态单一；「连贯长文本比打乱更伤性能」这个反直觉结果，作者自己写「we do not have a definitive answer for why」。
9. **HumanLayer 已不是 approval API。** 它现在定位是「Multiplayer Coding Agent IDE + Cloud」，官网没有 `require_approval` 这类接口文档。C2 只把它当「闸门放在设计文档阶段」的**产品主张**证据（弱），不能当技术方案抄。
10. **OTel GenAI semconv 未定版。** 全部标 `Development`，字段名可能变（本次已经因为迁库改过一次抓取地址）。照抄可以，但**不要**把它当稳定契约写进我们的交付契约。
11. **状态枚举的可比性是有限的。** Temporal 管的是 workflow execution，不是「卡片」；K8s Lease 管的是 holder，不是任务。§4 的表是**概念映射**，不是「同一层的东西」。
12. **本次没有做关键词广度检索。** `websearch` 全程返回空；所有来源都是「先知道名字，再去抓官方页」。⇒ 可能存在我没覆盖到的重要工作（尤其学术侧：CHI/CSCW/ACL 里关于 multi-agent 协作与 human oversight 的实证）。**建议下一位调研席补这一块**，用可用的检索后端，关键词至少包括：`multi-agent failure taxonomy`、`human oversight automation bias LLM`、`agent handoff context loss`、`role bleed multi-agent`。

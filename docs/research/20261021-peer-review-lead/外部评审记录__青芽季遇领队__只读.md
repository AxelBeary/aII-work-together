## 一、对方原话（三条 + 两条附带）

### 1 它确实比我们那套强，但只强在四题上

题 1（看板说谎）、题 4（交接块无限增长）、题 6（git 索引共享）、题 8（长任务白烧），本项目都有真实现，而且是结构性的：

- 一卡一行数据库；
- 状态靠**事件重放**而不是写死；
- append-only 是**「表根本没有 UPDATE 接口」**而不是靠纪律；
- 超预算强制收尾。

> 其中题 4 的解法直接命中他们的病根：**权威日志（只追加）与现值快照（可重写）拆成两层**；他们的问题正是把这两样写在同一个只增文件里。

### 2 它不解题 7（全局资源锁），这一题对方比我们强

- 本项目**没有「全局资源锁」这个概念**；租约主键是**卡号** ⇒ 只能表达「这张卡被占」，表达不了「这台机器上的引擎只能跑一次」。
- 互斥全是**进程内**的锁，跨 13 个独立进程无效；
- 真正的全局重活是靠**「引擎类动作一律串行」的约定**回避掉的，设计文档把「引擎级动作回收风暴」列为暂不处理。
- 对方的判断：他们那个 Markdown 令牌文件反而是**跨进程可见**的，病根不在令牌，在解锁尺写成了「mtime > 30 分钟」这种可能永不成立的条件。

### 3 两件你可能会想知道的事

① 本项目 README 有 **4 处与代码不符**：

- 「有数字」判据已改成机器测；
- 「mkdir 独占」已迁到数据库；
- 「五道闸」实跑 15 道；
- audit 里还留着一条**查从来不存在的目录的死判据** ⇒ 恒 0 命中。

对方原话：「最后那条正是我们题 2 那个『死尺族』的活例，**长在你自己这个仓里**。」

② 已请 claude-opus-5-5 评审过本项目，三大风险都修了，但还开着 **5 个口子**：哈希链改 git 锚定、对账循环、ACP 接入、复核默认换引擎、席名随机后缀。

### 3d 的部分（本条是本轮真正抓到的东西）

对方说「audit 里还留着一条查从来不存在的目录的死判据 ⇒ 恒 0 命中」。回源核对后：**方向对，但具体位置要修正**。

`tools/cli.py::cmd_audit` 的真实情况：

1. 卡片的遍历 **没有** 漏卡——`CardRef.is_dir()` 查的是「库里有没有这张卡」，不是磁盘目录（5 张卡全进循环）。这一点对方说重了。
2. 但**租约类判据确实全瞎**：`d / "lease" / "active"` 落到 `board/cards/<id>/lease/active`，而租约早已迁到 SQLite `leases` 表，新架构下这个目录永远不会出现 ⇒ 「活跃租约 >1」「租约目录名非固定名」两条判据**恒 0 命中**。
3. 更关键的是**缺判据**：库里状态与租约表之间没有任何交叉校验，手改 `cards.state` 或手写 journal 事件都能骗过 audit 直接报绿。

⇒ 结论：`python tools/board.py audit` 报「✓ 无绕过痕迹」在当前仓属于**部分假绿**（租约维度完全没查）。这正是本项目纪律里写的「死尺」——**任何 0 命中都要配一条必须非零的对照**。

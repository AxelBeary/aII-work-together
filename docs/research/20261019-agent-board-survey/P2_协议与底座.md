## 1 任务与范围

回答：**要让多个 agent 共享一块任务板，哪些「层」已经有事实标准/成熟底座，可以直接站在上面，而不是自己造？**

必须覆盖的六个方向（每方向至少 1 条，**总数 ≥10 条**）：

1. **agent 间协作协议**：`A2A`（Agent2Agent，Google 起、后交 Linux Foundation）、`ACP`（Agent Client Protocol，Zed）、`AG-UI`、其它 task/agent registry 类协议 —— 各自**解决的到底是哪一层**。
2. **工具/上下文接入**：`MCP`（Model Context Protocol）—— 能否当作「看板 ↔ agent」的接口层，还是只适合当工具层。
3. **本机 agent 的既有约定**：各家 CLI agent 的**无头调用形态**（`codex exec`／`opencode run`／`claude -p` 等）与**任务交接约定**（`AGENTS.md` 标准的普及度、`.agents` 目录约定、hook/子代理机制）——即「看板怎么把一张卡变成一个真的 agent 进程」。
4. **任务真相的持久化与状态同步**：`Temporal`／`Restate`／`DBOS` 这类 durable execution；`Yjs`／`Automerge` 这类 CRDT 协作同步；两者与「看板卡状态机」的契合度与代价。
5. **多 agent 协作的失败模式研究**：共享黑板（blackboard）经典架构、多 agent 编队的已知失效（瞎干活/互相覆盖/自报完成/上下文丢失）——**要的是「哪些设计被证明会坏」**，用于反向定我们的红线。
6. **可观测**：`OpenTelemetry` GenAI/agent 语义约定 —— 是否值得为此上 tracing（**注意：本机既有纪律把 OTel 分布式 tracing 列为负收益，本席必须给出「什么规模才值得」的判断依据**）。

每条给出：名称＋链接（访问日期）／成熟度（谁是维护方、有无正式规范、有无多家实现）／**它解决哪一层**／接入代价（人话：接它要写多少东西）／**契合判定** `可用`／`部分可用`／`不可用`／`未证`／**一句话结论**。

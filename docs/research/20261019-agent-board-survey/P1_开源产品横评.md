# 派工单 P1 · 开源「多 agent 协作看板」产品与轮子横评

- 席号：**调研席 A** ｜ 日期：2026-10-19 ｜ 发起：发牌席
- 父总单：`00_派工总单.md`（共同纪律以总单为准）

## 1 任务与范围

回答：**做「多 agent 在一块看板里分工协作」这件事，现成的开源产品/项目已经做到什么程度？** 哪些能直接用、哪些只能借思路、哪些是死路。

必须覆盖的三类（每类至少 3 个具体项目，**总数 ≥12 个**）：

- **类 1 · agent 原生任务板/编排 UI**：给 AI coding agent 用的看板或工作站（关键词：`agent kanban`、`vibe-kanban`、`claude squad`、`conductor`、`crystal`、`omnara`、`sculptor`、`terragon`、`autogen studio`、`langgraph studio`）。
- **类 2 · 通用开源看板（可被改造为 agent 看板）**：`Plane`、`Focalboard`、`Vikunja`、`Huly`、`Wekan`、`Taiga`、`OpenProject`、`Kanboard`、`Leantime`。
- **类 3 · agent 任务队列/共享黑板范式**：`claude-task-master`（Taskmaster AI）、`OpenHands`、`MetaGPT`、`ChatDev`、`AutoGen`/`AG2`、以及任何把「任务队列 + 多 agent 认领」做成产品的项目。

每个项目给这些维度（**每格必须有出处，没有就写 `未证`**）：

| 维度 | 说明 |
|---|---|
| 项目名＋链接 | 仓库/官网 URL（带访问日期） |
| 许可证 | MIT / Apache-2.0 / AGPL-3.0 / 闭源 …（**AGPL 要标出来**） |
| 技术栈与形态 | 语言、Web/CLI/桌面、是否需常驻服务、部署难度 |
| 协作模型 | 谁派活、谁认领、有无锁/租约、有无心跳、有无审批位 |
| agent 接入方式 | 支持哪些引擎、是否通用适配层、是否只支持自家 agent |
| 状态与证据 | 完成态怎么判（自报？看 diff？跑闸门？）、有无留痕 |
| 活跃度 | 最近提交时间/发版/star 数（**写明看到该数字的日期**） |
| **可用性判定** | `可用`／`部分可用`／`不可用`／`未证` |
| 对我们最有价值的点 / 最致命的缺点 | 各一两句人话 |

## 4 完成判定（发牌席可核对）

- `PASS`：交件存在；含 ≥12 个具体项目且**每个都有链接**；≥12 个项目里 `可用/部分可用` 判定非空的 ≥10 个；含非零计数句（「核过 N 条，采信 M 条」）；含首节能力边界声明。
- `BLOCKED`：无法联网 → 首节写明，且**⛔ 不许凭记忆编造**；此时改交「未证清单＋建议的替代取数路径」。
- `FAIL`：交件缺失、无链接、或出现明显编造的版本号/star 数。

## 一、候选能力清单（22 条）

### C-01 · 活性两把尺：心跳只证「进程活着」，还要证「在推进」

- **谁在做**：Temporal（<https://docs.temporal.io/evaluate/use-cases-design-patterns>，直读）。原话：「Report progress with an **Activity Heartbeat** so a job that dies mid-run is detected before its Start-To-Close Timeout expires, and **resumes from its last reported checkpoint**」。
  同一页还点名了「假死」这个经典故障：「A message queue with a five-minute visibility timeout **hands the same message to a second consumer while the first is still working**」——即：只按超时判死，会把还活着的活派给第二个人。
- **为什么必要**：心跳只能证明「编排器还在转」，证明不了「引擎在产出」。一个在死循环里打转的 agent，心跳照打，租约永不过期，卡永远停在「进行中」。
- **我们的现状**：**半个**。有 `lease` + `heartbeat`（TTL 600s、120s 一拍）＋超时回收留痕（`tools/board.py` L93、L348-388），但判据只有「有没有心跳」，没有「本轮有没有新产出/新事件」。**未证**项：`orchestrator.py` 的心跳是独立线程还是包在引擎调用外层——若是后者，引擎挂死会自然停拍，「假死」风险其实已被挡住。需主代理核一行代码即可定案。
- **建议优先级**：**P1**

### C-02 · 真正的「停止/吊销」：回收租约必须同时掐死执行者

- **谁在做**：Claude Code（<https://docs.claude.com/en/docs/claude-code/agent-view>，直读）。原话：「A reply that is exactly `/stop`: **stops the session at once** instead of being delivered to it」；另有 `claude stop <id>`、`Ctrl+X` 停止、`Stopped` 状态。
  GitHub Actions（<https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency>，直读）：「**cancel-in-progress: true**」、「GitHub Actions will cancel any workflow or job already running with that key」。
- **为什么必要**：我们的 `reclaim` 只做「把租约目录挪进 `lease/reclaimed/` + 记一条 event」。原进程没人管。于是出现最坏组合：租约判给 B，A 的引擎还在写同一批文件——**直接违反第 5 条硬纪律「一个路径一个写者」**，而且盘上不会报错，只会在几小时后发现文件被两版内容来回覆盖。
- **我们的现状**：**没有**。`AGENTS.md` §4.1 自己写明了这条边界：「挡不住被回收的进程已经在外面干过的事」。代码侧 `tools/*.py` 里 `kill` 只出现在 `term.py`（杀内置终端的子进程），没有按卡片杀引擎进程的路径。
- **建议优先级**：**P0**

### C-03 · 单卡预算/时长/轮数硬上限（熔断），不是仅统计

- **谁在做**：
  - Claude Code（<https://docs.claude.com/en/docs/claude-code/costs>，直读）有 `--max-budget-usd` 上限，并把 `/usage` 做成账本：「Total cost: $0.55 / Total duration (API): 6m 20s」；另有工作区级花费上限（「Cap spend … workspace spend limits」）。
  - Claude Code 子代理（<https://docs.claude.com/en/docs/claude-code/sub-agents>，直读）有 `maxTurns`：「Maximum number of agentic turns before the subagent stops.」
  - GitHub Copilot（<https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent>，直读）：「Each Copilot cloud agent session has a maximum execution time of **59 minutes**. This limit cannot be extended or bypassed.」
  - CrewAI（<https://docs.crewai.com/en/concepts/tasks>，直读）用 `guardrail_max_retries`（默认 3）给「不合格就重做」封顶。
- **为什么必要**：引擎坏在「不报错地多跑」上——一轮对话把整个上下文反复送来送去，成本是指数的；卡片没有上限时，编排器会一直喂卡片直到队列空。我们的 `usage` 是**事后账本**，不是**事中刹车**。
- **我们的现状**：**半个**。有用量/花费统计（README「用量/花费统计」），但 grep `budget|max_cost|cost_limit|max_turns|deadline` 在 `tools/*.py` **0 命中**。即：能看见花了多少，不能阻止它花。
- **建议优先级**：**P0**

### C-04 · 「需要人」与「失败」要主动推给你，而不是等你看页面

- **谁在做**：
  - Claude Code hooks（<https://docs.claude.com/en/docs/claude-code/hooks>，直读）把 `Notification` 做成一级事件，matcher 里直接列了 `agent_needs_input`、`agent_completed`；agent view 页写明「Claude Code also sends a notification … when a local background session **starts needing your input, finishes, or fails**」。
  - PagerDuty（<https://support.pagerduty.com/docs/escalation-policies>，直读）：「designed to **notify a single target at a time until one individual acknowledges**」、「There is **no delay before this first notification**」——即「无人应答就继续升级」，靠机制而不是靠人盯。
- **为什么必要**：本仓硬纪律第 3 条写着「退化必须可见……禁止静默转绿或静默跳过」。但现在「可见」的全部实现是**看板上的颜色**：没人打开窗口就等于不可见。真实故障：卡停在「拍板中」六小时，你以为 agent 在干；或引擎 401 掉了，卡在「进行中」烂到租约超时。
- **我们的现状**：**没有**。grep `toast|notify|notification|winotify|msgbox` 在 `tools/*.py` **0 命中**（托盘只有图标与双击进窗口）。
- **建议优先级**：**P0/P1 之间**——机制上我认为是 P1（不伤数据），但它是第 3 条纪律唯一的落地缺口，建议按 **P1 最高档**排。**注意**：任何弹窗/托盘气泡都属于「在用户桌面产生可见物」，按 §10 红线必须先取得你当场同意，所以这条要你点头才做。

### C-05 · 任务依赖（blocked_by / DAG）：B 必须等 A 的产物

- **谁在做**：CrewAI（<https://docs.crewai.com/en/concepts/tasks>，直读）：`context=[research_task]` 的注释原话是「**This task will wait for research_task to complete**」；`context` 可列多个，「use the `context` attribute to define in a future task that it **should wait for the output** of the asynchronous task」。Temporal 同页（直读）把「fan-out / map-reduce / batch iterator」列为标准形态。
- **为什么必要**：我们的纪律是「契约先钉死 → 再按文件发牌」。但只要有一次编排器先捡了「按契约实现」的卡、契约卡还在跑，产出就是照着旧版契约写的，白干一轮；而且它不会「失败」，会「成功但错」，最难查。
- **我们的现状**：**没有**。卡片只有自由文本 `blocked_reason`（`board.py` L278/L313），没有「前置卡号」这种边，编排器也就无法据此排序。现在的替代是「你在建卡时自己排好顺序」。
- **建议优先级**：**P1**（体量小：加一个 `depends_on: []` 字段 + 选取时过滤，不需要图算法）

### C-06 · 运行中能「偷看」当前输出，而不是等跑完

- **谁在做**：
  - Claude Code agent view（直读）：「Press `Space` to open the **peek panel**. It shows the session's **most recent output**, or the question it's waiting on, **rather than the full transcript**」；shell 侧还有 `claude logs <id>`「show recent output」。
  - HumanLayer（<https://www.humanlayer.dev/>，直读）主打「**Full session visibility** — … letting you drill into every thinking message, every subagent tool call, and every code change」。
- **为什么必要**：判断「它是在想还是在转圈」，唯一可靠信号是最近几十行输出。现在卡片只显示「进行中」，你对一个跑了 40 分钟的卡没有任何止损依据——只能等。
- **我们的现状**：**半个**。跑完会落 `run__<seat>__<hash>.json`（`orchestrator.py` L243 写 `r.text`），但那是**收尾一次性落盘**；界面/终端没有尾随。
- **建议优先级**：**P1**

### C-07 · 错误分级：可重试 vs 不可重试 + 按 retry-after 退避

- **谁在做**：
  - Temporal（直读）专门有 `Non-Retryable Errors` 模式：「fail fast on a rejection that **no retry will fix**」——反过来说，其他错误都该重试。
  - Anthropic API（<https://docs.claude.com/en/api/rate-limits>，直读）：「When the response has a `retry-after` header, **wait that many seconds before retrying**」；并明确花超额度的 429 **不带** `retry-after`、重试无效。
- **为什么必要**：现在 `engines.py` 只把 stderr 前 200 字符塞进 `reason`（L260、L286）。于是「529 上游天气」和「鉴权失败」在板上长得一样，都变成一次「失败」。按你的成本口径（成本＝往返次数），一次误判就是一次白跑＋一次人工复位。
- **我们的现状**：**半个/未证**。有「空跑」判定（`无 text 事件（可能空跑）`），但没有可重试性分类、没有退避、没有 `retry-after` 解析。
- **建议优先级**：**P1**

### C-08 · 拍板时要能看见「改了什么」，不是只看文件路径

- **谁在做**：HumanLayer（直读）把「code diffs」和「plan artifacts」并列成核心卖点：「brings agent sessions, plan artifacts, and **code diffs** together」；Copilot（直读）交付形态是 PR：「review changes and request refinements before creating a pull request」。Claude Code（<https://docs.claude.com/en/docs/claude-code/checkpointing>，直读）提供「**Restore code and conversation** / Restore conversation / Restore code」三档回退。
- **为什么必要**：你的验收动作是「照人话清单＋截图看」，而 L2 只验字节/行数。一份 40KB 的产物，字节数对、必含项命中，但内容被整段替换成废话——三道闸全过。人在拍板位上却没有 diff，等于「签字看不到合同」。
- **我们的现状**：**半个**。有 L2 形制＋L3 含数字，没有「上次拍板版 → 本版」的差异视图；`checkpointing` 式回退也没有（我们有 worktree 隔离，但那是「不进主树」，不是「可回退的快照」）。
- **建议优先级**：**P1**（最小形态：拍板抽屉里并排显示「上次通过版 vs 本版」的前 N 行差异 + 变更行数）

### C-09 · 计划先行闸：先出方案、人点头、再动手

- **谁在做**：Claude Code（<https://docs.claude.com/en/docs/claude-code/permission-modes>，直读）：「**edits stay blocked until you approve the plan**」；选项含「Yes, manually approve edits / No, keep planning」，还能 `Ctrl+G` 直接把计划拿到编辑器里改。HumanLayer 把它做成六阶段（QRSPI），口号「**Catch mistakes before 2,000 lines of code**」。
- **为什么必要**：返工的最大来源是「方向错了但已经写完」。我们靠「驳回理由回传下一轮」补救，属于事后。
- **我们的现状**：**半个**。卡有 `goal`，但没有「plan → 人批 → 执行」这个中间态（状态机里没有「计划待批」）。
- **建议优先级**：**P2**（会加重你的拍板负担，跟你「单轮最多 3-4 条」的带宽冲突；建议只在「大卡（>1 天量）」上启用）

### C-10 · 工具级权限：deny 优先、按命令粒度、可被 hook 拦

- **谁在做**：Claude Code（直读，hooks 页 + permission-modes 页）：`PreToolUse` 事件「**Can block it**」，示例就是拦 `rm -rf`；权限模式页写明「**Deny rules block in every mode**, including `bypassPermissions`」。
- **为什么必要**：我们唯一真正的白名单是**界面里的内置终端**（`term.py`），而真正干活的是引擎本体——它能跑什么完全取决于引擎自己的权限设置。也就是说，「不许碰生产」「不许 push」这类红线，目前靠纪律文本，不靠机制。
- **我们的现状**：**半个**。终端白名单有（且做得比多数产品严：不走 shell、管道重定向直接拒）；引擎侧无统一拦截面。
- **建议优先级**：**P1**（最便宜的一步：编排器启动引擎时统一注入一份 deny 清单，并在派工单里回读确认生效）

### C-11 · 沙箱与出网白名单（防数据外泄）

- **谁在做**：GitHub Copilot（<https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-the-firewall>，直读）：「By default, Copilot's access to the internet is **limited by a firewall**」、「Limiting internet access helps manage **data exfiltration risks**」；被拦时会把「blocked address 和尝试执行的命令」写进 PR。执行环境是「**ephemeral** development environment」（<https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment>）。
- **为什么必要**：本机 agent 跑在真实桌面、真实 `C:\Users`、真实密钥文件旁边。一次把 `.env` 贴进外呼提示，就是不可逆泄漏。
- **我们的现状**：**没有**（引擎裸跑本机，无出网约束；只有「禁投桌面／禁改外部件」这类文本纪律）。
- **建议优先级**：**P2**（做真沙箱成本很高，且与「用本机 CLI 引擎」这个前提打架；便宜的替代见 §3）
- **我们的现状补充**：这条我们**没做但也没假装做了**，属于「已知接受的残余风险」，应写进 `ENVIRONMENT.md` 而不是悄悄挂着。

### C-12 · 每一步的轨迹与成本归因（tracing），不是只有最终结果

- **谁在做**：Langfuse（<https://langfuse.com/docs/observability/overview>，直读）：「structured logs of every request that capture **the exact prompt sent, the model's response, token usage, latency**, and any tools or retrieval steps in between」；Claude Code 用 OpenTelemetry 导出「per-user token and cost metrics」（costs 页，直读）。
- **为什么必要**：一张卡花了 3 块钱，你想知道是哪一轮、哪个子代理烧的——现在只能看总数。成本优化没有归因就只能猜。
- **我们的现状**：**半个**。journal 有事件序列、`run__*.json` 有全文，但没有「每轮 token/耗时/工具调用」的结构化表。
- **建议优先级**：**P2**（先把 C-03 的硬上限做了，归因才有用武之地）

### C-13 · 产出的结构化契约：expected_output + 不过就带反馈重试

- **谁在做**：CrewAI（直读）：`expected_output` 是必填项（「A detailed description of what the task's completion looks like」）；guardrail 失败时「the error is **sent back to the agent**, and the task is retried up to `guardrail_max_retries` times」。Promptfoo（<https://www.promptfoo.dev/docs/configuration/expected-outputs/>，直读）把断言做成可组合集，含 `cost`、`latency`、`is-json` 等阈值型断言。
- **为什么必要**：我们现在的 L3 是「必含项命中 + 有数字」，这是**单向闸**：不过就 FAIL，人来看。而「带具体理由打回让它自己再试一轮」能省掉一整次人工往返——正好命中你「成本＝往返次数」的口径。
- **我们的现状**：**半个**（有 L3，且「驳回理由回传下一轮」已有；缺「自动带反馈重试 N 次」与「结构化 schema 判定」）。
- **建议优先级**：**P1**（复用现有驳回管道，只加计数与上限）

### C-14 · 并发组与去重：同一件事不许跑两遍

- **谁在做**：GitHub Actions（直读）：「only a single job or workflow using the same **concurrency group** will run at a time」；默认行为是「any existing `pending` job … will be **canceled**」。
- **为什么必要**：`mkdir` 认领解决了「同一张卡两人抢」，但解决不了「同一件事建了两张卡」——重复的卡会各自跑一遍，各自花一遍钱，还各自写一版产出。
- **我们的现状**：**半个**（卡级互斥有，跨卡判重没有）。
- **建议优先级**：**P2**

### C-15 · 生命周期钩子：让外部脚本挂在「状态变化」上

- **谁在做**：Claude Code hooks（直读）列了 20+ 事件（`SessionStart`/`PreToolUse`/`PostToolUse`/`Stop`/`SubagentStop`/`TaskCompleted`/`WorktreeCreate`/`PreCompact`…），且支持 command / HTTP / MCP / prompt / agent 五种处理器。Copilot 侧也有「Hooks can run commands during agent work for validation or logging」。
- **为什么必要**：一旦有钩子，「写日志到别处」「跑完自动 lint」「出问题发通知」都不用改主程序。
- **我们的现状**：**半个**（journal 是事实源、闸门是硬编码；没有对外的事件订阅口）。
- **建议优先级**：**P2**（C-04 可以先硬编码一条通知，不必先造钩子系统——避免过度工程）

### C-16 · 云端/跨机执行（关机也能跑）

- **谁在做**：OpenAI Codex Cloud（<https://developers.openai.com/codex/cloud>，直读）：「Each task has its own workspace and can keep working **while your computer is asleep**」；HumanLayer（直读）：「A local daemon runs many Agent sessions in parallel on your laptop. **Spin up cloud daemons** for long-running work … Agents keep working even if you close your laptop」。
- **为什么必要**（对别人）：长任务。
- **我们的现状**：**没有**（本机单机）。
- **建议优先级**：**P2 · 建议不做**（理由见 §3-3）

### C-17 · 常驻调度器（cron/事件触发自动开工）

- **谁在做**：Copilot Automations（直读）：「define a task once and have Copilot cloud agent run it **on a schedule or in response to repository events**」；Temporal Schedule；Inngest（<https://www.inngest.com/docs/features/inngest-functions/steps-workflows/step-ai-orchestration>，直读）把每次模型调用做成可重试 step。
- **为什么必要**（对别人）：无人值守。
- **我们的现状**：**没有**，且你已明确拍板「不做守护进程」。
- **建议优先级**：**P2 · 建议不做**（见 §3-1）

### C-18 · 移动端/远程接管 + SSO/RBAC

- **谁在做**：HumanLayer（直读）：「same UI on web, desktop, or **phone**」；Enterprise 档「SSO/SAML、Audit Logs」。Claude Code remote control：「monitor and steer a GitHub Copilot CLI session from GitHub.com」。
- **我们的现状**：**没有**。
- **建议优先级**：**P2 · 建议不做**（单人本机；见 §3-2）

### C-19 · 多 agent 自由对话/聊天室

- **谁在做**：不少框架都有「agents 互相聊到收敛」的形态（这一条我**没有**找到可引用的官方表述，故不点名——见 §4「未证」）。
- **我们的现状**：**没有，且 D-013 已明确不做**（`AGENTS.md` §3.1：「⛔ 不做『聊天室』：无终止条件、且会让多方同时获得写权导致术语串味」）。
- **建议优先级**：**P2 · 建议不做**（见 §3-4）

### C-20 · 长期记忆/知识沉淀（跨会话）

- **谁在做**：Copilot Memory（直读）：「builds a **longer-term, persistent understanding** of your repositories and preferences across sessions」；Claude Code 的 `CLAUDE.md` / `memory` 字段。
- **我们的现状**：**有，而且比多数产品细**：`AGENTS.md`（纪律）＋ `DECISIONS.md`（拍板）＋ `ENVIRONMENT.md`（坑，带可复跑命令）＋ `HANDOFF.md`（交接块）＋ `.opencode/memory`。
- **建议优先级**：**不新增**（列为「我们做得更好」，别被外面的话术带着再加一层）

### C-21 · 会话回退（rewind）与「代码/对话分开还原」

- **谁在做**：Claude Code checkpointing（直读）：每次提问生成一个 checkpoint，保留最近 100 个；可「Restore code and conversation / Restore conversation / Restore code」，还能「Summarize from here」。并诚实列了三条限制：Bash 改的文件不跟踪、子代理改动不还原、外部改动不跟踪。
- **为什么必要**：agent 走错方向时，「退回到上一个好状态」比「让它改回来」便宜得多，也更可信。
- **我们的现状**：**半个**。worktree 保证不污染主树、收工只拷交付物；但没有卡级快照与「退回上一版并重跑」。
- **建议优先级**：**P2**（worktree + git 已覆盖大部分风险，性价比不如 C-02/C-03）

### C-22 · 「可执行的状态机」而不是「一串 if」

- **谁在做**：Temporal（直读）把状态机当独立用例：「a state machine … usually means a transition table, a persistence layer for the current state, and **a job to detect rows that got stuck** — none of which is the process you set out to model」。
- **我们的现状**：**有**（`board.py` 状态机 + journal 重放），三条红线都落在具体命令的拒绝路径上——这点比多数产品扎实。
- **建议优先级**：**不新增**（列为「我们做得对」）

## 二、我们真的缺（按优先级排，共 7 条）

> 只列「不做会出事」的，不列「做了更好」的。每条都写「不做会发生什么」。

| 序 | 缺什么 | 对应 | 不做会发生什么 |
|---|---|---|---|
| 1 | **回收租约时不杀进程** | C-02 | 租约判给 B 之后，A 的引擎仍在写同一批文件。两次写、无报错、盘上留一版混合内容。**这是唯一一条会直接违反我们第 5 条硬纪律的缺口**，而且违反时系统全程绿灯：闸门只看最终文件，不看「谁写的」。 |
| 2 | **单卡成本/时长/轮数没有上限** | C-03 | 一个在循环里打转的卡（引擎不报错、每次都「正常返回」）能把一天的预算烧掉，而且**不可逆**——钱花出去退不回来，worktree 也可以重建，钱不行。现在只有事后账单，没有事中刹车。 |
| 3 | **「需要人/失败」不推送** | C-04 | 卡停在「拍板中」或引擎 401 掉了，你只有在打开窗口时才可能发现。硬纪律第 3 条「退化必须可见」目前只落在**颜色**上，等于把「可见」寄托在「你恰好看了一眼」。最坏情况：你以为在跑，实际队列已经空了两小时。 |
| 4 | **卡与卡之间没有前置关系** | C-05 | 编排器可能先做「按契约实现」、后做「定契约」。产物不会失败，只会「成功但按旧契约写」，返工一轮且极难归因（因为三道闸全过）。 |
| 5 | **运行中看不到当前输出** | C-06 | 一个跑偏的卡要烧满 40 分钟你才有机会判断；40 分钟里你无法区分「在深思」与「在转圈」。同时这也让 C-01 的「在推进」判据没法落地——没有中间输出，就没有判断素材。 |
| 6 | **错误不分可重试/不可重试** | C-07 | 一次上游 529（天气）和一次鉴权失败在板上长得一样，都记一次失败、都吃一次人工。按你的口径，每次误判＝一次白跑的往返。 |
| 7 | **拍板看不到 diff** | C-08 | 内容被整段替换但字节数、必含项都对 → 三道闸全过 → 你在没有差异视图的情况下拍板。**这条最伤「状态即证据」的可信度**：证据存在，但人不具备判读它的界面。 |

**P0 只有 1 与 2 两条**。理由：只有这两条的后果是「不可逆 + 系统自己不会报警」。第 3 条虽然也是纪律缺口，但它是「延迟发现」而非「破坏」；第 7 条是「看得见但看不清」，可以通过人工加一道 `git diff` 临时顶住。

**建议先做哪一条**：**第 1 条（C-02，回收即杀进程）**。它工作量最小（`reclaim` 时按卡记录的 pid/session 杀掉 + 留痕），却堵的是唯一会**静默破坏产物**的洞；而且它做完之后，C-01 的「假死」也不会再演变成双写——两件事一起收敛。

## 三、看起来必要、其实我们可以不做（4 条）

> 目的：防堆功能。每条都写清「为什么不必」，以及「不做要付什么代价」（代价照实写，不粉饰）。

### §3-1 常驻调度器 / cron 自动开工（C-17）

外面几乎人人都有（Copilot Automations、Temporal Schedule、Inngest 事件触发），看起来是编排工具的标配。
**为什么不必**：你已经明确拍板不做守护进程，这是对的——单人本机场景下，守护进程带来的三个成本（自启残留、静默烧钱、出问题没人当场叫停）都远大于「夜里多干几小时」的收益。
**代价照实说**：队列只在你手动 `run` 时推进；「攒一夜活、早上收」这种用法不支持。
**替代**：真要无人值守，用一条**一次性** `schtasks` 任务（跑完即删），而不是常驻服务。

### §3-2 移动端/远程接管 + SSO/RBAC（C-18）

HumanLayer 把它当卖点（phone、SSO/SAML、audit logs）。
**为什么不必**：这些能力解决的是「多人 + 多机 + 合规」。我们是「一个人 + 一台机 + 无外部用户」——RBAC 没有第二个主体可授权，SSO 没有第二个身份要登，手机看板等于在 6 寸屏上重做一遍桌面 UI。
**代价照实说**：离开电脑就完全失控；卡在跑的时候你没法远程叫停。这一点由 C-04（提醒）＋C-02（停止）在本机补上即可，不需要远程。

### §3-3 云端/跨机执行（C-16）

Codex Cloud 的「电脑睡着也继续跑」确实诱人。
**为什么不必**：我们的三个引擎（codex/opencode/qoderclicn）都是**本机 CLI**，把执行搬到云上等于换掉整个执行臂，并新增密钥分发、代码上传、结果回传三条新风险面。而它换来的只是「关机也能跑」。
**代价照实说**：本机休眠＝全线停；长任务被睡眠打断（`ENVIRONMENT.md` 已有同类坑）。缓解成本极低：跑长任务前禁休眠。

### §3-4 多 agent 自由对话/聊天室（C-19）

**为什么不必**：`D-013` 已经拍过：无终止条件，且多方同时拿到写权会导致术语串味。我们现在的替代（点对点评审「评审席只准看 + 逐字节比对」）在**可追责**上严格优于自由对话。
**代价照实说**：拿不到「多个 agent 互相启发」的涌现效果。这条我建议长期不翻案——它和「一个路径一个写者」在原理上冲突。

### 4.2 反推（多篇说法一致，但我没找到一句能直接引的话）

- **「agent 空转/假死」是行业公认故障**：是由 Temporal 的心跳段、Claude Code agent view 的状态表（`Working`/`Idle`/`Failed`/`Stopped` + 「a session can come back unresponsive」）、PagerDuty 的「无人应答就升级」三处**一起**推出来的。没有任何一家直接写「我们的产品能检测 agent 空转」。
- **「审批必须看 diff」**：HumanLayer 把 `code diffs` 与 artifacts 并列、Copilot 以 PR 为交付面——两处形态一致，但都**没写**「没有 diff 就无法审批」这句因果。
- **「预算熔断优于事后统计」**：Claude Code 同时提供账本（`/usage`）和上限（`--max-budget-usd`），Copilot 只给硬时长上限——从「两家都选择做上限、且都做在账单之外」反推上限是必需品，但这是推断不是原文。
- **「结构化产出 + 带反馈重试能省人工往返」**：CrewAI 的 guardrail 注释说「error is sent back to the agent」，Promptfoo 提供阈值断言；「因此省一次人工」是我按你的成本口径推的，产品文档没这么说。

## 五、附：我们做得比外部好的地方（别被话术带着改）

这几条外面常见，我们已经有且更严，**不建议动**：

| 能力 | 外面的形态 | 我们的形态 |
|---|---|---|
| 证据闸门 | Copilot「Logs do not replace your own review and testing」；Claude Code 无「证据」概念 | L1/L2/L3 三道闸 + **异会话复核**（复核席==执行席直接拒）——比「让同一个 agent 自己说做完了」严 |
| 人闸不可绕 | 多数产品是「权限提示」（可被 `bypassPermissions` 一次关掉） | 令牌 + `human` 子命令，agent 拓扑上无法自推（D-014 族） |
| 一个路径一个写者 | worktree 隔离为主 | worktree + **交付物路径重叠且内容不同 ⇒ BLOCKED**（不静默覆盖） |
| 知识沉淀 | Copilot Memory（黑箱持久理解） | `AGENTS.md`/`DECISIONS`/`ENVIRONMENT`（带可复跑命令）/`HANDOFF` 四件明账 |
| 播报分母 | 多数只报「完成」 | 强制「N of M + 口径 + 实测时刻」 |

**唯一被外部明确比下去的**：`ENVIRONMENT.md` 里有坑、`AGENTS.md` 里有纪律，但**没有一条「外部脚本可挂的事件口」**（C-15）——这不是缺陷，是取舍，等 C-04 真做了再说。

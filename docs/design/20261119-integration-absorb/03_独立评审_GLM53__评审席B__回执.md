## 结论：CONCERNS

方向正确（单一内核账本、契约先行、闸门带反空跑），但技术核心「fork 边界」未证当已证，P2 的工期与验收闸全部悬空。

## 关键发现（按影响排序）

F1｜硬伤：「只改三处」不成立（已读代码）
store.mutate 调用点分布在 6 个文件：routes.ts 12 处、scheduler.ts 11 处、session-sync.ts 10 处、execution.ts 9 处、external-sync.ts 6 处、tools.ts 6 处。方案只列 store/tools/execution。routes.ts 是面板自身 HTTP 写面（task-created :812、task-moved :937、task-deleted :1093、ledger-replaced :1428），不改它，「面板写操作必须落到 journal」这条 P2 验收闸物理上无法达成。方案 §10 自己写「store 是否只经少数方法落盘：未逐方法核对」，§4 却直接下了「只改三处」结论。

F2｜硬伤：CQRS 大概率退化成双写（已读代码+推断）
mutate(kind, mutator) 的契约是闭包直接变形 ledger 文档（store.ts:255–268）。闭包无法跨进程转发：要么逐调用点重写成内核 API（=重写 6 文件，P2 两三周打不住），要么本地照跑再镜像（=双写）。方案没有给出闭包→内核写的映射机制，这是 P2 的技术核心，缺了它 P2 不可估算。

F3｜断言核实：①taskboard 随包全量 TS 源码 ✅（已读盘）；②server.py Host 校验+页面 token ✅（:67/:722/:783，已读代码）；③dsh 不在 PATH ✅（where.exe exit=1，已实测）；④BBFF ledger 是 agent 名册派生库 ✅（ledger.js:1 自述 derived/rebuildable）；⑤❌（见 F1）；⑥❌ 高风险（见 F2）。

F4｜调度双轨没关死（已读代码）：内核 tick 触发 due 任务后仍需经 scheduler.ts 的 11 处 mutate 落状态，P1 没有这张票。

F5｜公理漏项（推断）：备份/恢复没进任何验收闸（dock kill -9 后 SQLite WAL 尾部撕裂的恢复路径未写）；schema 演进（v1→v2 旧事件怎么读）无票；token 是页面级单把（server.py:67），MCP/DSH 多面共用＝一面泄漏全线失守，P0 契约里没有 per-face 凭据。

F6｜低估的坑 8 条（概率×损失）：①按三文件开工两周后发现闭包不可转发→重做（高×高）；②双写静默形成、audit 报链断（中×高）；③单 token 多面泄漏（低×高）；④WAL 撕裂（低×高）；⑤Python 20 闸与 TS 面零交叉回归（高×中）；⑥tick 与残留调度并发（中×中）；⑦taskboard 0.11 上游改 store 契约（中×中）；⑧ProcGuardTray 退役窗双守望并发（低×中）。

## 更好的替代（A'）

保留「内核唯一账本」；但 DSH 面不走 fork 换心脏，改做 KernelStore 适配器：写一个类实现 store 的四个公开方法（snapshot/get/subscribe/mutate），mutate 在本地不落盘副本上跑闭包→按 8 种 kind 推内核 upsert，内核按状态机白名单校验（agent 面 upsert 到 done 必须拒）。routes.ts/TaskBoard.tsx 零改动，改动面从 6 文件缩到 store.ts+装配点。CQRS 不退化：本地无持久化即无双写。这正是 00 稿「不 fork、走 HTTP」与 01 稿「fork」之间的正解——许可放开不该导致过度升级。

过度设计可砍：P5（BBFF role→seat）整段砍，seat 已够用，省 1 周+上游 API 风险；MCP 20 个工具面（10 正名+10 别名）推迟到有人真用 MCP 客户端再做；P6 subtree 合并改为永不合并，hub 只放 contracts+adapters，避免 Apache/MIT 混仓与 47k 行 vendor 负担；fork 里直接摘除 external-sync（禅道/TAPD）这条第二写路径。

## 对 P0–P2 的具体修改

- P0 加 T0：「store 写路径清单」——6 文件×52 处 mutate 逐点映射（kind→内核 API→内核侧校验），先做它再冻结 fork 边界（工作量 1 天，方案 §10 自己欠的账）。
- P0 契约补三条：schema 演进策略；备份/恢复闸（损坏账本 30 分钟恢复实测）；per-face 凭据设计。
- P1 加票：tick→due 任务→scheduler 写路径的归并设计（F4）。
- P2 改口径：验收闸补「agent 面经 KernelStore upsert done ⇒ 内核拒绝并留事件」；工期按适配器方案重估（约 1–1.5 周，非 2–3 周）。
- P5/MCP/P6 合并：砍或推迟（见上）。

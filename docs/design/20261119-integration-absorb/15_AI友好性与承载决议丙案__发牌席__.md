## 1 为什么 meta 是错的（我上一稿推荐错了）

`storage.py:245-271` 写卡时把 `meta` 当整体 JSON 读出来、改、再写回：

```python
meta = card.get("meta") or {}
# ... 整块写回 ...
```

⇒ **两个并发写者会互相覆盖**。comments 恰恰是追加型数据，用 meta 就是拿「最后写入者赢」的语义去存本该追加的日志。这是设计错误，不是性能取舍。

`tools/cli.py:619` 还有一处 `if k != "meta"` 直接把它排除在展示之外——说明 meta 现在本就是「不透明的杂物间」，不适合当正式承载位。

## 2 为什么 events 表天然合适（已核实）

```
events(seq INTEGER PRIMARY KEY AUTOINCREMENT,
       card_id, at, at_ms, type, data TEXT, prev TEXT, hash TEXT)
CREATE INDEX idx_events_card ON events(card_id, seq)
```

四个属性正好对上四类数据：

| 属性 | 代码位置 | 对 AI 的价值 |
|---|---|---|
| **append-only** | `storage.py:325 append_event` 只 INSERT | 追加永不覆盖，并发安全 |
| **每卡单调 `seq`** | AUTOINCREMENT + 索引 | **天然增量游标**：`?since=seq` 即可拉新 |
| **哈希链** | `_hash(prev, obj)` @321 | 篡改可检测，无需另建审计 |
| **`data` 是自由 JSON** | `json.dumps(data)` | 任意结构直接放，无需改表 |

**关键点：内核的 `replay()` 已经证明这套能工作**——它把事件流折叠成状态。comments/executions/checklist 只是「更多可折叠的事件类型」，不需要新机制。

## 3 丙案具体做法

### 3.1 新增事件类型（不改表结构）

| 数据 | 事件类型 | 折叠规则 |
|---|---|---|
| 评论 | `comment` | 追加；`deliveredAt` 用后续 `comment-delivered` 事件表示 |
| 执行记录 | `execution-open` / `execution-close` / `execution-activity` | 折叠成「最后一次 open 未被 close 的即 running」 |
| 验收清单 | `checklist-add` / `checklist-check` / `checklist-uncheck` | 逐项折叠成当前清单 |
| 分支 | `branch-set` | 最后一次为准 |
| 软删除 | `trash` / `restore` | 折叠成 `trashed_at` |

### 3.2 幂等：`idempotency_key` 进事件

`append_event` 加唯一索引 `(card_id, idem_key)`，重放同 key 直接返回原事件。**这是 AI 最需要的特性**——agent 重试不会写两条。

### 3.3 增量拉取：`since=seq`

`GET /api/card/events?id=...&since=123` → 只回 `seq > 123` 的事件。
面板轮询、适配器同步、SSE 全用同一个游标，**不需要全量重读**。

## 4 AI 友好性的其余四条（同样重要）

### 4.1 结构化错误，而不是人类话术

现状 `board.py:136 die()` 只 `print("✗ …")` + `exit(1)`。agent 只能靠正则猜。

```json
{"ok": false, "error": {"code": "version_conflict", "message": "…",
 "hint": "先 board show <id> 取最新 version，再带 --if-version 重试",
 "retryable": true}}
```

**`code` 闭集**（与 taskboard 对齐，少造新词）：
`invalid_input` / `not_found` / `version_conflict` / `invalid_transition` / `forbidden` / `busy` / `blocked` / `internal`

### 4.2 `--json` 全覆盖

现状只有 6 处有 `--json`。**每个写命令都要有**，且失败时也输出 JSON（不是 `die()` 打断）。

### 4.3 一次调用就能知道下一步

写命令的 JSON 里固定带 `next`：
```json
{"ok": true, "value": {...}, "next": ["board submit C1 --seat w1 --epoch 3"]}
```
agent 不需要读文档猜流程。

### 4.4 能力自描述

`board schema --json` 输出全部命令、参数、约束、状态机边。**agent 可自举**，不用人喂文档。

## 5 对契约的影响（改 `task-envelope-v1`）

删除 `meta` 承载假设，改为：

| 字段 | 变化 |
|---|---|
| `events` | 不再内嵌；由 `?since=seq` 单独拉 |
| `meta` | 降级为「不透明扩展」，⛔ 不用于 comments/executions |
| `seq` | **新增为顶层字段**：该卡当前最新事件 seq，作乐观并发与增量同步双用 |
| `version` | 保留（卡字段版本），与 `seq` 分离：`version` 管字段并发，`seq` 管事件流位置 |

### 那条失败是什么

```
✗ 幂等重放只留 1 条 — 重放 3 次产生 3 条（期望 1）
```

**实测确认**：`events` 表列为 `seq, card_id, at, at_ms, type, data, prev, hash`——**没有 `idem_key`**，`append_event` 无幂等检查。
用测试把需求钉住：P1 补上唯一索引后，这条会**自动转绿**。

### 为什么这是「AI 友好」的关键

agent 最大的风险是**重试**（超时、断连、宿主重启）。没有幂等键，一次重试就多一条 comment / 多一次执行记录。
有了它，agent 可以无脑重试——这是把「小心别重复」的纪律变成**结构上不可能重复**。

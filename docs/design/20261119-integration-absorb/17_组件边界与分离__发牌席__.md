# 组件边界：什么留在内核，什么单独提出去

> 2026-11-20 · 回答「哨兵坞、信箱后台要不要单独提出去」。
> 结论：**要**。按「账本 / 监督 / 传输 / 派工」四层切开，只留契约，不合并进程与仓库。

---

## 1 四层与归属

| 层 | 组件 | 职责 | 放哪 | 为什么 |
|---|---|---|---|---|
| **账本层** | aII-work-together 内核（本仓） | 卡、状态机、证据、租约、人闸、调度、HTTP/CLI/MCP | **本仓** | 唯一真相；零依赖、可离线跑 |
| **派工层** | Oh-My-BBFF | 谁去干、任务书、角色权限、模型分档 | **外部，pin 版本** | 用户明确要保留；上游活跃 |
| **监督层** | sentinel-dock（哨兵坞） | 进程托管、拉起、审计、托盘、Job Object | **独立仓库/组件** | 需要杀进程权限与常驻生命周期，和账本不是一个失败域 |
| **传输层** | waypost（信箱后台） | 跨机信箱、唤醒、裁决回传 | **独立仓库/组件** | 跑在**别的机器**上；本机只是其中一端 |
| 面板适配 | faces/dsh-taskboard | 把 taskboard UI 接到内核 | 本仓（薄适配） | 只是 HTTP 映射，无状态 |
| 遗留 | sentinel-ops | 旧脚本+托盘 | 逐步被 dock 插件替代 | 不新增能力，只做迁移 |

---

## 2 为什么不能合进内核（三条硬理由）

1. **失败域不同**：内核挂了只是不能记账；监督层挂了要能**把内核拉起来**。合成一个进程，监督者自己死了没人管它。
2. **权限不同**：dock 有杀进程、Job Object、托盘的能力；内核只需要读写自己的库。合并等于给账本发了一把刀。
3. **生命周期不同**：waypost 在别的机器常驻；内核是「有人用才开」的服务。同一仓库会逼出错误的启动假设。

---

## 3 三条契约（分开之后靠这个接）

### 3.1 监督契约（dock → 内核）

本仓提供 `deploy/supervise.json`（**提案格式，dock 尚未实现读取**）：

```json
{
  "version": 1,
  "services": [
    { "id": "board-server", "cmd": ["python", "tools/server.py", "--port", "8790"],
      "cwd": ".", "health": "http://127.0.0.1:8790/api/state",
      "restart": "on-failure", "maxRestarts": 5 },
    { "id": "board-tick", "cmd": ["python", "tools/board.py", "tick"],
      "cwd": ".", "schedule": "*/30 * * * *", "restart": "never" }
  ]
}
```

dock 只需支持：`cmd/cwd/health/restart/schedule` 五项，就能接管内核与 tick。

### 3.2 传输契约（waypost ↔ 内核）

- 收信 → 建卡：`POST /api/card`，带 `source.kind=peer`、`source.ref=<信封 id>`、`idempotency_key=<信封 id>`。
- 取结果 → 回信：`GET /api/card/events?id=&since=`，按 `execution-close` / `review` 事件生成回执。
- 对端输入一律当**不可信**：只允许建卡与追加评论，⛔ 不允许直接改状态或批准。

### 3.3 派工契约（BBFF → 内核）

- Lead 派出的工作 → 一条卡：`assignee.role` 保留原角色 id，`source.ref` 指回 Lead 会话。
- 角色完成后按内核证据协议提交；⛔ 内核不自己选角色、不绕过 Lead 收口。

---

## 4 明确不做

- ⛔ 不把 dock（Rust）并进本仓 Python 树。
- ⛔ 不把 waypost 的哨兵循环并进 `tools/`：它是另一台机器的进程。
- ⛔ 不让内核直接杀进程 / 起托盘——那是 dock 的职责。
- ⛔ 不把调度再挪出去：调度已经在内核（D-037），因为「错过窗口留痕」属于账本语义。

---

## 5 迁移顺序（低风险）

1. **先定契约**（本文 + `deploy/supervise.json`），两边都不改代码。
2. dock 实现 manifest 读取，先只托管 `board-server`（dry-run 一周）。
3. waypost 增加「信封 → 内核建卡」适配（不改哨兵主体）。
4. sentinel-ops 的 proc-watchdog 在 dock 等价能力验证后退役。

## 7 子代理编排：调用，不插入

> 2026-11-20 · 回答「子代理编排插件是插入这个看板还是调用」。

**实现上调用，界面上挂入口。**

| 问题 | 答案 | 理由 |
|---|---|---|
| 编排代码进内核仓库吗 | ⛔ 不进 | 内核是零依赖 Python 账本；编排是 DSH/Node 侧决策 |
| 看板负责派谁吗 | ⛔ 不负责 | 派工是 BBFF Lead 的职责（D-039），看板只记「谁领了、干到哪」 |
| 编排插件嵌进看板面板吗 | ⛔ 不嵌 | 面板是 DSH 插件；编排也是 DSH 插件，二者是**兄弟**，不是父子 |
| 界面能有入口吗 | ✅ 能 | 面板可以放「派工 / 看编排状态」按钮，点了去调编排插件，不是内联执行 |
| 数据怎么流 | 编排 → 看板 | `board ready/claim/beat/submit/msg` 或 HTTP；看板**不回调用编排** |

**为什么不能反过来**：

1. **无头可用**：看板要能在没有 DSH、没有编排插件时被 cron/tick/waypost 用；嵌进去就绑死了。
2. **失败隔离**：编排崩了，账本不能跟着崩；账本崩了，编排还能重启它（dock 的职责）。
3. **可替换**：BBFF、内置 subagent、外部 CLI 是三种编排实现；看板一旦内嵌一种，就排他了。
4. **闸门可信**：内核 21 道闸是纯 Python 自证；引入 Node 运行时会让「看板自检」依赖插件生态。

**唯一允许的耦合点**：卡的 `source.ref` 指回编排会话，`assignee.role` 保留原角色 id——这是**数据字段**，不是代码依赖。

---

## 6 一句话

**内核只做账本；哨兵坞只做活着；信箱只做跨机；BBFF 只做派工。四者用 HTTP/文件契约连接，不共享进程，不共享仓库。**

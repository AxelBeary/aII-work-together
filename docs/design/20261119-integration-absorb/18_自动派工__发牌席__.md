# 自动派工：谁触发、调谁、怎么停

> 2026-11-20 · D-043。回答「想要自动派工，或者自动调用 BBFF 或 CLI」。
> 实现：`tools/autodispatch.py`（参考编排器，**不属于内核账本**）。

## 1 它是什么

一个独立守护进程：轮询看板「可开工」的卡，按配置调用执行器。

```bash
# 只看会派什么，不动卡（默认）
python tools/autodispatch.py once --adapter cli

# 真派：复用现有 orchestrator（CLI 引擎）
python tools/autodispatch.py run --adapter cli --apply --interval 20

# 调任意命令（stdin 环境变量带卡号；将来 BBFF CLI 就挂这里）
python tools/autodispatch.py run --adapter cmd --command "your-bbff-cli dispatch" --apply

# 调 HTTP webhook（DSH 侧桥接器/远程执行器）
python tools/autodispatch.py run --adapter http --url http://127.0.0.1:9001/dispatch --apply
```

## 2 三种 adapter

| adapter | 调什么 | 现状 |
|---|---|---|
| `cli` | `tools/orchestrator.py run --max 1` | ✅ 已实测 |
| `cmd` | 任意命令，环境变量 `BOARD_CARD / BOARD_TITLE` | ✅ 已实测（stub） |
| `http` | POST `{card, project}` | ✅ 代码就绪，未接真实桥 |

## 3 安全设计（默认不失控）

- **不加 `--apply` 只打印**，不动任何卡。
- **单实例锁** `board/.autodispatch.lock`。
- **在飞跳过**：最近 `dispatch-start` 未收口（15 分钟）不重派。
- **失败冷却**：`dispatch-end` 后卡仍是可派状态 ⇒ 10 分钟内不重派（防止每轮空转）。
- **每步留痕**：`dispatch-start` / `dispatch-end`（含 rc、耗时、输出摘要），可审计。
- **回收站跳过**：不派已软删的卡。

## 4 BBFF 怎么接（当前事实）

BBFF **没有 CLI**（`package.json` 无 `bin`，只有 DSH 插件）。所以现在不能用 `cmd` 直接调它。

两条可行路径：

1. **http 桥**（推荐）：写一个 DSH 侧接收端，收到 POST 后用 `cross_session_send` 把任务发给 BBFF Lead；
   autodispatch 用 `--adapter http --url ...`。
2. **未来上游提供 CLI**：若 BBFF 出 `bbff dispatch`，直接 `--adapter cmd --command "bbff dispatch"`。

⛔ 不伪造 BBFF 的派工决策，也不把编排逻辑塞回内核（D-042）。

## 5 和调度（D-037）的分工

- **调度**回答「什么时候该有卡」——在内核，因为错过窗口留痕属于账本语义。
- **自动派工**回答「卡有了派给谁」——在外部，因为选择执行器是编排决策。

两者都通过 `tick` / `dispatch-start` 留痕，互不越界。

## 6 启用建议

先手动跑一周 `once --adapter cli`（不加 `--apply`）看它选卡是否符合预期，再开 `run --apply`。

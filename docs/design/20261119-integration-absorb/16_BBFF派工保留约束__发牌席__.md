# BBFF 派工模型：保留约束（硬）

> 用户 2026-11-19：**「他这个派工我很喜欢，尽可能保留好」**。
> 结论：BBFF 的派工是**本体能力**，不是可被内核替代的实现细节。整合只做适配，⛔ 不重写、不压平。

---

## 1 要保留的到底是什么

从上游仓库与本地包读出的派工模型（`packages/oh-my-bbff-team/lib/{doctrine,catalog,role-permissions}.js`）：

| 要素 | 具体内容 | 为什么不能丢 |
|---|---|---|
| **Lead 是经理不是执行者** | Lead 只做拆解、派工、审阅、汇报；不亲自实现非平凡工作 | 这是整套方法的根基：派工质量决定产出质量 |
| **角色目录** | explorer / librarian / oracle / designer / fixer / writer / laborer（+ tester） | 不同任务找不同人，是「知道该找谁」的前提 |
| **角色任务书（leaderBrief）** | 每个角色带 whenToUse / whenNotToUse / deliverable / boundaries | 派工不靠临场发挥，靠写好的边界 |
| **权限在工具层强制** | explorer / oracle 只读；fixer 可写；按角色给权限 | 光靠提示词约束不算约束 |
| **模型分档** | 每个角色有模型档位，Lead 显式选择 | 成本与能力匹配 |
| **核心席 / 外包席** | 核心席长期在位、承接常规职责；外包席做有界任务、可复用 | 团队稳定性和成本的分界 |
| **嵌套与并发上限** | nestingMode（helpers / outsourced）、单角色并发上限 | 防止无限套娃与资源爆炸 |
| **名册与活动可观测** | roster / activity / 最近工具调用 | Lead 能发现成员跑偏或卡死 |

---

## 2 整合边界（谁改什么）

| 层 | 归属 | 允许的改动 |
|---|---|---|
| 派工决策（谁做什么、任务书怎么写） | **BBFF Lead** | ⛔ 不改；内核不参与 |
| 角色目录、权限、模型档位 | **BBFF** | ⛔ 不改；只读引用 |
| 任务账本（卡、证据、租约、人闸） | **本仓 kernel** | ✅ 由我们改 |
| 两者之间的桥 | 适配层（新写） | ✅ 只做映射，不改两边语义 |

**一句话**：BBFF 决定「谁去干」，内核决定「干了什么、算不算完成」。两者不互相替代。

---

## 3 适配层要做的事（只做三件）

1. **席位映射**：BBFF 的角色名 → 内核的 `seat`（`role` 字段保留原角色 id）。
   ⛔ 不把角色压成「w1/w2」丢掉语义。
2. **派工可见**：Lead 派出去的任务，在内核里是一条卡（`source.kind=agent`，`source.ref=<Lead 会话 id>`）。
3. **结果回传**：角色干完按内核协议提交证据（`execution-report` / `submit`）；
   ⛔ 不允许角色直接改卡状态绕过 Lead 的收口。

---

## 4 明确不做（防止「整合」把派工做没）

- ⛔ 不把 BBFF 的角色目录复制进内核（会分裂成两份真相）。
- ⛔ 不让内核自己决定派谁（那是 Lead 的职责）。
- ⛔ 不把「核心席/外包席」压成同一种执行者。
- ⛔ 不绕过 BBFF 的权限闸（read-only 角色在内核侧也只能读）。
- ⛔ 不在 P6 合并仓库时把 BBFF vendor 进来（上游活跃，pin 版本 + 适配层）。

---

## 5 验收（怎么证明「保留好了」）

| 检查 | 判据 |
|---|---|
| Lead 仍是唯一派工者 | 内核里没有「自动选角色」的代码路径 |
| 角色语义完整 | 卡的 `assignee.role` 能取到 explorer/fixer/oracle 等原值 |
| 权限仍在工具层 | read-only 角色调内核写接口必须被拒（拒绝数 ≥1） |
| 任务书可追溯 | 卡的 `meta.brief` 能回指 Lead 写的任务书 |
| 不 vendor | 仓库里没有 BBFF 源码副本；依赖是 pin 的包 |

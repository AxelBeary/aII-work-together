## 一、一句话结论

**架构是通的，但有一条硬矛盾必须你先拍板**：
你选的「文件即卡」（D-001 第 1 条）让**红线②（人的拍板位）在技术上无法强制**——
因为卡就是磁盘上的普通文件，**本机任何 agent 都能直接改它**，「只有人能把卡推出拍板列」这句话在文件系统层没有落点。

三席一致给出的解法是：**卡文件仍然唯一事实源，但写权收归看板进程**——agent 不再直接写卡，只调接口。
这样不违背你的「文件即卡」决定，变的只是「谁持有写句柄」。**这一条需要你点头。**

## 二、卡片长什么样（D1，已亲验：34 字段／8 态／17 边／12 不变量）

**一句话**：一张卡＝**一个目录**，目录里的 `journal.jsonl` 是唯一真相，`card.md` 只是给人看的派生快照。

```
board/cards/<card-id>/
  card.md          # 人读：目标/领地/交付物/验收判据（建卡时写，之后只读）
  journal.jsonl    # 唯一真相：append-only，一次状态迁移一条
  lease/           # 租约（见第三节）
  artifacts/       # 产物：每个席位写自己命名的文件
  evidence/        # 凭据
```

**8 个状态**：待认领 → 进行中 →（待验收 → 核验中 →）完成；旁支：阻塞／拍板中／已取消
**17 条转移边**，每条都规定了「谁能触发 + 必须带什么证据」。
**12 条不变量**，其中 9 条是「强制」（写路径拒写），3 条是「检测」（对账器抓）。

**agent 绝对不许触发的转移**（红线②的拓扑落点）：出 `拍板中` 的所有边，actor 白名单只有人。

## 三、怎么保证「只有一个人干活」（D2，已亲验：45,375 字节／518 行）

**这是本轮最漂亮的一个解法**，正面回答了「文件形态下怎么原子认领」：

> **认领不是「去改卡」，而是「原子地独占创建一个专属路径」。**

租约＝一个**目录**，身份直接编码在目录名里：

```
lease/active/L__<席号>__<engine>__<epoch_ms>__<nonce>/
```

两个 agent 同时抢 ⇒ 两个进程同时 `mkdir` 同一个路径 ⇒ **文件系统保证恰好一个成功**。
排他性**不来自**「先读后写」（有 TOCTOU 竞态），也不来自「加锁标志位」（有写一半被杀的空窗），**只来自创建动作本身**。

D2 还给了三种做法的对照表，把前两种判为 `不可用`／`部分可用`——这是很硬的工程判断。

**但有个前提**：这个原语只在**本机磁盘**上可靠。⛔ 看板数据目录不能放 OneDrive／网络盘。

## 四、什么才算完成（D2，本席认为这是最有价值的一节）

**退出码在这个体系里的权重＝0。**

理由三条（D2 §B.0）：① 四家引擎的退出码全可被证伪；② 退出码描述「进程怎么结束的」，不是「世界上发生了什么」——**范畴错误**；③ 引擎回执属于自证，不能进正档。

**完成＝四层全过 + 人位**：

| 层 | 考什么 | 谁跑 | 不过怎么办 |
|---|---|---|---|
| **L1** 产物存在性 | 文件在不在、字节>0、mtime 在时间窗内 | 机器 | 停在 verify |
| **L2** 形制 | 字节/行数/md5、编码、JSON 可解析 | 机器 | 打回 |
| **L3** 内容闸门 | 派工单声明的必含项逐条断言 | 机器 | 打回 |
| **L4** 独立复核 | **另开会话**复跑 L1–L3 + 另找反例 | **复核席**（⛔ 不能是执行者） | PASS/FAIL |
| **人位** | 拍板项、对外交付、红线争议 | **人** | 卡停在拍板列 |

**逐引擎判据**（⛔ 没有「统一解析」）：Hermes 看 `--usage-file` 的 `completed`；codex 必须见 `turn.completed`；qoderclicn 看 `is_error` 且**不用会谎报的 `subtype`**；opencode 看 `type:"text"` 且**不用 RC**。

## 五、三条红线的真实强度（**这是本轮最重要的诚实结论**）

D1 没有为了让设计好看而放宽红线，而是标了 `冲突`。我认为这个判断是对的：

| 红线 | 能保证什么 | **不能保证什么** | 强制力 |
|---|---|---|---|
| ① 状态即证据 | 保证「**有**证据」 | **不能保证「证据真」**（假 sha256 可写进去） | **强制**（无证据进不了完成） |
| ② 人的拍板位 | 保证「**拓扑上**绕不过人闸」 | **不能保证「磁盘上没人绕过写路径」** | ⚠️ **冲突 C-01** |
| ③ 认领即租约 | 保证「同一时刻只有一个**卡写者**」 | **不能保证「没有两个进程在外面干活」**（被回收的旧进程可能已经干了） | 本机本地卷＝强制；外部副作用管不住 ⚠️ **冲突 C-02** |

**这三句话我建议原样写进产品文档**——它比「我们实现了三条红线」诚实得多，而且它精确指出了二期要补什么。

## 六、MAST 给的反向校验（D3，已亲验：14 类失效逐条）

把 14 类已知失效对着我们的红线打表，结果是：

> **三条红线只能直接防住 2 类（14 类里）。**

完全覆盖不到的 5 类，按优先级：
1. **FM-3.3 错验（占 9.1%，最高）**——agent 验证自己做的东西
2. FM-2.3 跑偏（7.4%）
3. FM-1.4 丢上下文（2.8%）
4. FM-2.1 对话重置（2.2%）
5. FM-2.5 无视他人输入（1.9%）

**这不是坏消息，是设计输入**：它告诉我们一期最容易翻车的地方不是「认领」，而是**「验证质量」**。而 D2 的 L4 独立复核（另开会话 + 另找反例）恰好就是对 FM-3.3 的正面回答。

## 1 任务

首轮调研给出两个「值得深挖」的件，本席把它们挖到可用程度：

1. **`openai/symphony` 的 `SPEC.md`**——首轮判定它是**唯一「规格级可抄」**的件（Apache-2.0）。
2. **MAST 论文**（arXiv `2503.13657`）——150 条轨迹 → 14 类失效、3 大类。

## 2 必须产出

**(A) Symphony SPEC 逐节精读**
- 打开 `https://github.com/openai/symphony/blob/main/SPEC.md`（访问日期必须写）
- 逐节抽出：**调度状态机**（有哪些状态、怎么转）、**claim 防重复怎么做的**、**并发上限怎么控**、**重试与回收策略**、**状态对账（reconciliation）机制**、**结构化日志字段**
- 每节给：**规格原文要点（转述，不整段抄）／我们的看板能直接用什么／哪里不适用及为什么**
- ⚠️ 特别注意：Symphony 是给 **coding agent + issue tracker** 设计的。**明确指出哪些假设在我们「多引擎、含非编码 agent」的场景下会破**

**(B) MAST 14 类失效 → 我们的设计对策**
- 把 14 类失效（分属：系统设计／agent 间错位／任务验证）**逐条列表**
- 每条给：**失效原文含义（转述）／在我们场景里会不会发生／我们的哪条红线或机制能防住／防不住的话缺什么**
- ⚠️ 这是本批最重要的产出：**它把「我们的红线」从经验判断升级为「对着已知失效分类逐条对照」**
- 明确标出：**MAST 有哪几类失效，我们的三条红线覆盖不到**（这是要补的设计缺口）

**(C) 两者合并的「设计输入清单」**
给 D1／D2 两位设计席的**具体输入**：哪些机制该照抄、哪些要改、哪些要新造。写成可执行的条目（例：「认领要用 SPEC §X 的 claim 语义，但把 tracker 换成卡片文件」）。

**(D) 未证清单**
- 未核到的节／未读到的原文
- 论文里「适用于我们的场景」属于推断的部分要显式标出

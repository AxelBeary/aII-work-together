# 裁决：意见卡住要不要扣返工额度

- 席号：评审席（异会话挑刺，只判不改）
- 日期：2026-10-23
- 立场：先假设「不该做」，再找能推翻它的证据（未找到）
- 判据来源：只读源码与文档，**未跑任何 `board` / `orchestrator` / `check.py`**

---

## 1 结论

**不做原提案**（「同一条意见第 2 轮仍未解决 ⇒ 自动扣返工额度」）。
**改条件做它的目标**：把额度从「复核后才结算」挪到「派工前就拦」，stuck 意见**只留痕、不扣分**。

一句话理由：这**不是**「两套各管一段的半截刹车」，而是**两条路上各自已经完整的刹车**。把它们焊在一起 =
① 同一个 `fail` 事件被计两次；② 「扣多少」在默认参数下是个假问题；③ 惩罚的恰恰是「逐轮如实登记同一 ID」的复核席。

---

## 2 理由（5 条）

**R1 · 两套机制读同一份事件流，扣额度＝重复计数。**
`attempts()` 直接数 `type=="review" and verdict!="pass"`（`tools/board.py:282-288`）。而「第 2 轮仍 open」必然发生在一个 fail 复核里——`cmd_review` 明文禁止「带 open 意见给 PASS」（`tools/cli.py:850-853`）⇒ 那一轮**已经扣过 1 次额度**。再按意见扣一次，是同一件事记两遍账。

**R2 · 「按条扣／按轮扣／扣到底」在默认配置下是同一个终局，问题 2 的三选一是假选择。**
- R1 fail（T1 open）：`attempts=1 / limit=3 / left=2`
- R2 fail（T1 仍 open ⇒ stuck）：`attempts=2 / left=1`
- stuck 最早只能出现在第 2 轮（`cli.py:856-862` 要拿此轮 open 与上一轮 open 取交集）

⇒ 出现 stuck 时，桌面上**只剩 1 点额度**，任何 `d≥1` 都立刻把 `left` 打到 0。三种扣法都等于「第 2 轮直接阻塞」。既然结果相同，就不存在「选一种温和的扣法」这个设计空间。

**R3 · 动 `attempts` 会顺手改掉「换更强模型」的触发条件（隐蔽耦合）。**
`orchestrator.py:317-318` 用 `count_attempts()` 决定 `pick_model()` 是否升级。若把罚分记进 `attempts`，一张卡就会因为「意见编号重名」而升级到强模型——而 `docs/research/20261021-escalation-experiment/饱和负载下的升级浪费__20261022.md` §3.2 要求升级**只跟结构信号（闸红）**，§2.3 与 §6 还给出 N01 反例证明强模型会把对的做成错的。
⇒ 硬约束：**任何罚分只能减 `retry_limit()`，⛔ 不许动 `attempts()`**。

**R4 · 它给「已经有两道刹车」的路再加闸，却碰不到真正没闸的那条路。**
- 自动路径（`orchestrator.py` 自己写的复核）**不带 items / round 字段**（`orchestrator.py:694-703`、`701-703`）⇒ D-026 的 stuck 与「三轮硬拦」在自动路径上**永不触发**。连带后果：`board show` 的「第 N 轮」对自动复核的卡恒显示「第 1 轮」（`cli.py:513-514` 的 `round or 1`）。
- 人手路径已经有两道：三轮硬拦（`cli.py:867-874`）＋ `show` 里逐条标「← 两轮未解决」（`cli.py:519-524`）。
⇒ 提案的净效果是「让人手路早一轮停」，自动路一分没变；而同一张卡的质量问题会因为「谁复核」而被两套标准处理。

**R5 · 提案想借的「自动进阻塞」现在根本拦不住工作。**
`board.claim` 允许认领 `阻塞` 态（`board.py:467`），`pick()` 把 `阻塞` 也算可接（`orchestrator.py:773`），而 `withholding()` 只查依赖与预算、**完全不查返工额度**（`board.py:801-820`）。于是「额度用尽 + 已阻塞」的卡再跑一次编排器，仍会被认领、烧掉一整轮引擎，直到复核时才在 `orchestrator.py:612-618` 判阻塞。
同理 `board retry` 会把「阻塞但 left>0」的卡直接派出去（`cli.py:98-109`）⇒ **任何「留着额度就写 block」的自动阻塞都会被下一次 retry 复活**。这才是缺口，且一行就能补（见 §4 件 A）。

## 3 反例（会被误伤的卡）

**F1 · 正在正常收敛的大卡（任何扣法都会打死）。**
第 1 轮复核给 T1–T5 五条 open；第 2 轮回来 T2–T5 全 fixed、只剩 T1 open。这是**4/5 已收敛**的健康卡，`attempts` 也才第 2 次。提案按条扣 1 ⇒ `left=0`，直接阻塞。
（现实里这种卡最常见：一轮意见往往写 5–8 条，分批修。）

**F2 · 换复核席导致 ID 语义漂移（假 stuck）。**
`cmd_review` 只取 `text[:300]`，**从不比对同一 ID 前后两轮的文本是否同一件事**（`cli.py:798-808`、`856-862`）。而现有闸测试本身就在换复核席（`tests/test_review_items.py:78-85` 用 `w3/w4`，其后又换 `w5/w6`）。第 2 轮的复核席完全可能把 `T1` 这个编号挪去指一个新问题 ⇒ 系统判「同一条意见卡住」，扣光额度。

**F3 · 「不列＝已解决」——最恶性的一条。**
stuck 是把「本轮 open 的 ID」与「**上一条** review 事件里的 open ID」取交集（`cli.py:857-862`，`prev_open` 每轮被覆盖）。所以第 2 轮复核席若只列新问题、压根不提 T1（既不标 open 也不标 fixed），T1 就从两侧消失 ⇒ stuck 为空 ⇒ 刹车不触发。**结果是：如实逐轮重列同一 ID 的复核席被罚，少写几条的复核席被放过。** 这正好把「状态即证据」反过来用：把「没写」当成「已解决」。
任何以「缺席即已解决」为输入的自动罚则，都会被这条反向激励污染，且没法靠加防御救回来。

**F4 · 机器闸红导致的 fail 与意见无关。**
`review_only` 在机器闸不过时会自动写一条 `verdict:"fail"` 的 review（`orchestrator.py:693-699`）。这类 fail 让 `attempts` 涨、但根本不产生 items；一张卡可能先被机器闸消耗 2 点，第 3 轮才轮到人给意见，此时再叠罚分 ⇒ 一条意见就把卡打死。

**F5 · 单条大意见天然需要三轮。**
如「整章译文语域串线」这种意见：第 1 轮提出 → 第 2 轮改了一半、复核席写「T1 仍 open」→ 第 3 轮才收敛。这是同一条 ID 连开 2 轮、且完全在正常节奏内。提案会在第 2 轮就把它判死。

## 4 若要做的具体改法

### 件 A（必做，替代原提案）：额度接进「派工前」

- 改动点：`tools/board.py:801` `withholding()`，在 `budget_status()` 之后追加：
  - 条件：`retry_left(cid, card) <= 0`
  - 产出原因字符串：`返工额度用尽（{attempts}/{limit}），要人 \`board retry --force\` 加额度`
- 效果：`orchestrator.pick()` 直接在派工前跳过并落日志（`orchestrator.py:775-780` 已有 skipped 日志通道），不再白烧一整轮引擎；`board retry` 的现有口径不变。
- 留痕：**不需新事件**（额度本身就是事件流里的 `review` × n 与 `retry_grant`），日志行由 `pick()` 承担。
- 要补的测试（追加进 `tests/test_retry.py`）：
  - `⑥ 额度用尽的卡不在派工名单里（withholding 非空，且 reason 含「额度用尽」）`
  - `⑥对照 额度未用尽的待返工卡 withholding 为空（证明不是把所有待返工都挡了）`
  - `⑦ 反空跑：把 RETRY_BASE 临时调成 0，同一张卡必须被挡（证明闸看的是额度、不是状态）`

### 件 B（可选，用户点头才做）：stuck 只留痕，不扣额度

- 事件名：`item_stuck`；字段 `{type, actor:"review", seat, ids:[...], round, review_seq, note}`
- 语义：`actor` 必须是 `review`（**不是** `system`），**不写 review 事件、不进 `attempts`**，只被 `board show` 与 `board retry` 的 reason 引用。
- 触发条件（写死，三个同时为真才算「真卡死」）：
  1. `stuck` 非空；
  2. 本轮 `items` 里 `state=="fixed"` 的条数为 0（**有任何进展就不算卡死**，直接解掉 F1/F5）；
  3. `review_rounds+1 >= 3`（与 D-026 闸③ 同一时点，不提前）。
- 扣减：**0 点。** 该停的时候由闸③ 的既有路径停。

### 若用户仍坚持「要扣」：唯一不误伤的形态（写死）

同时满足四条才扣，且**只减 `retry_limit()`、不动 `attempts()`**：
1. 同一 ID 连续 2 轮 `open`；
2. 该 ID 的 `text[:300]` 前后两轮 **sha8 相等**（防 F2 换席漂移）；
3. 本轮 `fixed` 条数为 0（防 F1）；
4. 上一轮 review 事件带 `items`（防 F4 机器闸 fail 混入）。

扣减量：`1`。并必须在 D-029 里写明：**在 `RETRY_BASE=3` 下这等价于「第 2 轮直接阻塞」**（理由见 R2），别把它宣传成「温和的一档」。

## 5 不做的代价（用现有机制，人到底多做几步）

按路径分开算，结论是**几乎为零**：

- **自动路径（编排器跑）**：已自动。`attempts >= limit` 时 `orchestrator.py:614-618` 自己写 `block`，人不在场也停。**人 0 步。**（唯一毛病是晚一轮，正是件 A 要修的。）
- **人手复核路径**：
  1. 卡到第 3 轮仍是同一 ID 时，`board review` 会**硬拦并打印两条现成命令**（`board block ... --reason "同一意见三轮未解决"` / `加 --force`，`cli.py:869-874`）；
  2. 人只做一次**二选一**；
  3. 想知道「还剩几条、哪条卡住」，`board show` 已渲染「意见 N 条，未关闭 M 条，其中卡住 K 条」＋逐条「← 两轮未解决」（`cli.py:519-524`），不用翻 JSONL。
- ⇒ 提案省下的是**一次复核往返（一次引擎调用）**，代价是引入一条会误伤 D-029 额度语义的自动罚则。按「治理体重上限」原则（新增规矩必须能点名它防住过的事故），这次点名不出来：它要防的「无限转圈」，D-026 闸③（人手路）与额度制（自动路）各自都已经防住了。

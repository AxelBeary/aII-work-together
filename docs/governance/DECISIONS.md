## D-001 · 项目形态与一期范围（**待拍板**）

- 日期：2026-10-19（依据段于 2026-10-19 首轮调研后补充）
- 议题：本项目的看板**以什么形态存在**、agent **怎么接进来**、**一期做到哪**、**治理强度**多高。
- 背景：项目 2026-10-19 立项，工作区 `E:\GithubClone\allworktogether`（此前为空，仅有 `.opencode/memory/project.md`）。用户诉求原话：「让所有 agent 在一个看板内分工协作」。
- 待拍板四条（建议值＝发牌席推荐，用户可全推翻）：

| # | 议题 | 选项 | 发牌席建议 |
|---|---|---|---|
| 1 | **形态** | A 本地 Web 看板（浏览器打开，本机跑）+ 后端守护<br>B 纯文件/CLI 编排层（无 UI，卡片＝文件＋命令行工具）<br>C 嵌入现有工具（opencode 插件／桌面端面板） | **A 为主、B 为底**：先落「文件即卡（单一事实源）＋ 一个薄 API」，再套 Web 看板；界面与引擎解耦 |
| 2 | **agent 接入** | A 本机 CLI 引擎（codex／qoderclicn／opencode／Hermes）为主<br>B 含外部 API／中转信道（RTOC）<br>C 可插拔通用适配层 | **C**，但一期只实做「本机 CLI 引擎适配器」一个真件，外部信道留接口 |
| 3 | **一期范围** | A 最小可用看板 + 一个真实任务端到端跑通（认领→执行→验收→完成）<br>B 先把调研/架构做完再动手 | **A**：先证明「闭环能跑」，再谈规模化 |
| 4 | **治理强度** | A 轻量（本文件级别）<br>B 重装（照 `sentinel-ops`：席位制＋分级闸门＋租约制全量） | **A 起步**，随规模再升档（避免给一个还没成形的产品套重装流程） |

### 依据（2026-10-19 首轮调研后补）

来源：`docs/research/20261019-agent-board-survey/98_合并摘要__发牌席__人话版.md`

1. **形态建议有据**：17 个开源产品中判 `可用` 者 **0 个**；缺的正是「跨引擎统一认领／心跳回收／完成＝证据／人的审批位不可越」四条，与 `AGENTS.md` §4 三条红线重合。⇒ 差异化不在 UI，在状态机 ⇒ 支持「B 为底、A 为面」。
2. **接入建议有据**：P2 判定所有现成协议（A2A／MCP／ACP／AG-UI／Temporal／Yjs…）**都不覆盖任务真相层**；且四个本机引擎的**退出码全部不能当成功判据**（P3）⇒ 完成判据必须自造，适配层必须可插拔。
3. **范围建议有据**：最接近我们的 KittyClaw 是 **AGPL-3.0**（改造后对外提供网络服务须开源全部改动），且仅 27 stars、新项目 ⇒ 不宜直接改造它；而 Symphony（**Apache-2.0**，规格级可抄：claim 防重复／并发上限／重试回收／状态对账）是最佳借鉴对象 ⇒ 自造薄层 + 抄规格，比改造现成产品更快到闭环。
4. **治理强度建议有据**：本项目尚无代码、无回归库；全局规则要求「首个施工批次开工前建最小回归库（≥10 条）」——先轻量起步、开工时再补回归库，符合「治理体重上限」。
5. **一条硬约束已明确**：未经用户当场同意不得在真实桌面产生可见物 ⇒ 一期**默认浏览器 Web 页**，⛔ 不做托盘／弹框／桌面通知。

- 影响面：目录结构、技术选型、派工路数、一期里程碑。
- 状态：**待拍板**

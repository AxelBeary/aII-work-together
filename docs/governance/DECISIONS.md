## D-013 · 多 agent 协作走「点对点评审」，不建聊天室（**已拍板** 2026-10-20）

- 日期：2026-10-20
- 议题：用户要「多 agent 互相讨论的聊天室／串流派工」，具体用例是 B 初翻 → B1/B2 提意见 → B 自己优化，且 B1/B2 可以是别的 agent 或别的提供商。
- 结论（用户 2026-10-20 拍板「做点对点」）：**只做点对点**，不做聊天室。B 初稿 → 评审席独立提意见 → B 自己改 → **改完回头验**。
- 依据：
  - 聊天室没有终止条件（会一直对话烧钱），而卡片有明确的「什么样算做完」。
  - 聊天室让多方同时获得写权 ⇒ 术语/语体会串味。本项目红线「一个路径一个写者」直接冲突。
  - 用户明确要求「别太臃肿，太多字我也不想看」。
- 强制约束（已落地并有测试）：
  - **评审席只准看**：评审前后逐字节比对交付物，被改则按原字节恢复 + 记 `consult_violation`，本轮作废。
  - **改后必须回头验**：修改轮之后自动再问同一批评审席「哪几条还没改」；没按格式回记 **未知**，⛔ 绝不当成 0。
- 影响面：`tools/consult.py`、`tools/orchestrator.py`（`run --consult`）、`tools/cli.py`（`board consult`）、`tools/server.py`＋`ui.html`（看板显示评审与未改条数）、`tests/test_consult.py`。
- 状态：**已拍板**

## D-011 · 存储换 SQLite + 团队规模（**已拍板** 2026-10-20）

- 日期：2026-10-20
- 指令：「换存储 SQLite」「打造成我们整个团队 几十个项目 都能同时使用的」
- 结论：

| 议题 | 裁定 |
|---|---|
| **卡片存储** | 文件即卡 → **SQLite**（每项目 `board/board.db`）。理由不是「更时髦」，而是**消除两个真缺陷的根因**：原子认领靠 `os.mkdir` 脆、journal 并发靠手写文件锁 |
| **写路径** | 每次写**独立连接 + `BEGIN IMMEDIATE`**（SQLite 官方推荐），天然支持多线程与多进程 |
| **读路径** | **每线程一个连接**（SQLite 连接不能跨线程共享，实测会 `bad parameter or other API misuse`） |
| **注册表** | JSON → **SQLite**（`~/.allworktogether/registry.db`）。多人多项目同时登记，JSON 会互相覆盖 |
| **跨项目** | `board all`（总览）／`board inbox --all`（汇总待拍板）／`orchestrator run-all`（跨项目编排） |
| **多人** | 每人一个 token（`~/.board-human-<who>.tok`）；归属记录进事件流；`BOARD_USER` 可固定身份 |
| **规模** | 实测 20 项目 × 15 卡 ＝ 300 张，冷扫描 **0.21s**，缓存 0.0004s |

**迁移**：首次运行自动把 `board/cards/*` 导入 `board.db`，旧文件保留作对照（`board/MIGRATED.txt` 记条数）。

**保留不换**：交付物仍是工作区里的普通文件（产物要人能直接看）；证据文件仍落盘。

- 状态：**已拍板**

## D-007 · 多项目 + 并行 + 易用性（**已拍板** 2026-10-19）

- 日期：2026-10-19
- 指令：用户「代码库可以逐渐规整了。开一堆 worktree 出去加速做完。吸纳所有值得吸纳的 让产品简单易用 目标是单人的最佳 agent 编排看板。可以多找找网上现成轮子 吸纳。需要支持多项目。」
- 结论：

| 议题 | 裁定 | 理由 |
|---|---|---|
| **多项目存储** | **数据跟项目走**：每个项目根目录一个 `board/`；全局注册表 `~/.allworktogether/projects.json` **只记位置** | 可 git、可搬、可单独备份；删注册表不伤数据 |
| **项目识别** | **零配置**：向上找 `board/cards`（像 git 找 `.git`）；任意目录直接 `board add` 自动建并登记 | 省掉「先 init」这一步 |
| **默认值** | **项目级默认引擎/模型/思考强度**，建卡自动继承 | 最大摩擦是每次手打模型名 |
| **并行** | **每卡一个 git worktree**，`--parallel N`，建议 ≤2 | 多 agent 改同一仓库会互踩；worktree 是干净解法 |
| **冲突** | 收工只拷该卡交付物；路径重叠且内容不同 ⇒ **BLOCKED** | 守住「一个路径一个写者」 |
| **代码规整** | 拆出 `render.py`／`projects.py`／`parallel.py`；`board.py` 仍是 CLI 入口 | 渐进式，不一次性大重构（风险高） |
| **易用性** | 裸 `board` 给面板不给报错；`add` 取代 `new`；`open` 一条命令看板 | 单人工具要少记命令 |

- **未采纳（明确记录）**：一次性把 `board.py` 拆成完整包——风险大于收益，改为按职责渐进拆，每次拆完跑回归。
- 影响面：`tools/` 全部；`AGENTS.md` §2／§3.1；`README`／`docs/usage.md`
- 状态：**已拍板**

## D-004 · 架构期四条待拍板项（**已定** 2026-10-19）

- 日期：2026-10-19

## D-014 · 跨会话留言：吸收 ocs 的语义，不搬它的传输（**已拍板** 2026-10-20）

- 日期：2026-10-20
- 议题：`HANDOFF` §五 #6 记着「未吸收 ocs 的跨会话消息」。用户 2026-10-20：**要**。
- 结论：抄**语义四条**，换掉**传输一层**。
  - 抄：① append-only ＋ 单调 seq（`--reply-to <seq>` 任何会话可寻址）；② `wake: HELD`（送达被拦要明说）；③ 退出码分档 `0 已投递 / 2 已存但唤不醒 / 3 没成`；④ **一律不重发**（按 seq 查，不靠重试灌重复）。
  - 换：ocs 靠常驻会话的唤醒通道（Claude socket / Codex IPC）；我们是「起进程等结果」，所以**唤醒＝拿 sessionID 续一次会话**（`opencode --session` / `qoderclicn --resume`），它答完的内容自动写成 `kind=answer`、`reply_to` 指回原 seq 的留言。没有 sessionID ⇒ 记 HELD，退出码 2。
- 落地：`tools/messages.py`、`tools/msgwake.py`、`board msg send|ls|inbox|ack|thread|wake|states`、存储两张 append-only 表（`messages` / `msg_reads` + `msg_wakes`）、闸 `tests/test_messages.py`（16 条）。
- 依据（实测，2026-10-20 56 分～58 分）：同一段流程跑通首存 → 收件箱 → 已读 → 回复链路；HELD 路径退出码 2 实测；「已回复过不重发」挡住第二次投递。
- 影响面：`storage.py`（新增三表，无 UPDATE/DELETE 接口）、`cli.py`（新增 `msg`）、`server.py`（`/api/messages*`）、界面（留言抽屉）。
- 已声明的边界：只保证「留言按 seq 存住了」；对方看没看只能靠它自己 `inbox`/`ack`。**同一条留言不要重复 wake**（实测重复投递会多出一条重复回复）。
- 状态：**已拍板**

## D-013 · 多 agent 协作走「点对点评审」，不建聊天室（**已拍板** 2026-10-20）

- 日期：2026-10-20
- 议题：用户要「多 agent 互相讨论的聊天室／串流派工」，具体用例是 B 初翻 → B1/B2 提意见 → B 自己优化，且 B1/B2 可以是别的 agent 或别的提供商。
- 结论（用户 2026-10-20 拍板「做点对点」）：**只做点对点**，不做聊天室。B 初稿 → 评审席独立提意见 → B 自己改 → **改完回头验**。
- 依据：
  - 聊天室没有终止条件（会一直对话烧钱），而卡片有明确的「什么样算做完」。
  - 聊天室让多方同时获得写权 ⇒ 术语/语体会串味。本项目红线「一个路径一个写者」直接冲突。
  - 用户明确要求「别太臃肿，太多字我也不想看」。
- 强制约束（已落地并有测试）：
  - **评审席只准看**：评审前后逐字节比对交付物，被改则按原字节恢复 + 记 `consult_violation`，本轮作废。
  - **改后必须回头验**：修改轮之后自动再问同一批评审席「哪几条还没改」；没按格式回记 **未知**，⛔ 绝不当成 0。
- 影响面：`tools/consult.py`、`tools/orchestrator.py`（`run --consult`）、`tools/cli.py`（`board consult`）、`tools/server.py`＋`ui.html`（看板显示评审与未改条数）、`tests/test_consult.py`。
- 状态：**已拍板**

## D-011 · 存储换 SQLite + 团队规模（**已拍板** 2026-10-20）

- 日期：2026-10-20
- 指令：「换存储 SQLite」「打造成我们整个团队 几十个项目 都能同时使用的」
- 结论：

| 议题 | 裁定 |
|---|---|
| **卡片存储** | 文件即卡 → **SQLite**（每项目 `board/board.db`）。理由不是「更时髦」，而是**消除两个真缺陷的根因**：原子认领靠 `os.mkdir` 脆、journal 并发靠手写文件锁 |
| **写路径** | 每次写**独立连接 + `BEGIN IMMEDIATE`**（SQLite 官方推荐），天然支持多线程与多进程 |
| **读路径** | **每线程一个连接**（SQLite 连接不能跨线程共享，实测会 `bad parameter or other API misuse`） |
| **注册表** | JSON → **SQLite**（`~/.aII-work-together/registry.db`）。多人多项目同时登记，JSON 会互相覆盖 |
| **跨项目** | `board all`（总览）／`board inbox --all`（汇总待拍板）／`orchestrator run-all`（跨项目编排） |
| **多人** | 每人一个 token（`~/.board-human-<who>.tok`）；归属记录进事件流；`BOARD_USER` 可固定身份 |
| **规模** | 实测 20 项目 × 15 卡 ＝ 300 张，冷扫描 **0.21s**，缓存 0.0004s |

**迁移**：首次运行自动把 `board/cards/*` 导入 `board.db`，旧文件保留作对照（`board/MIGRATED.txt` 记条数）。

**保留不换**：交付物仍是工作区里的普通文件（产物要人能直接看）；证据文件仍落盘。

- 状态：**已拍板**

## D-007 · 多项目 + 并行 + 易用性（**已拍板** 2026-10-19）

- 日期：2026-10-19
- 指令：用户「代码库可以逐渐规整了。开一堆 worktree 出去加速做完。吸纳所有值得吸纳的 让产品简单易用 目标是单人的最佳 agent 编排看板。可以多找找网上现成轮子 吸纳。需要支持多项目。」
- 结论：

| 议题 | 裁定 | 理由 |
|---|---|---|
| **多项目存储** | **数据跟项目走**：每个项目根目录一个 `board/`；全局注册表 `~/.aII-work-together/projects.json` **只记位置** | 可 git、可搬、可单独备份；删注册表不伤数据 |
| **项目识别** | **零配置**：向上找 `board/cards`（像 git 找 `.git`）；任意目录直接 `board add` 自动建并登记 | 省掉「先 init」这一步 |
| **默认值** | **项目级默认引擎/模型/思考强度**，建卡自动继承 | 最大摩擦是每次手打模型名 |
| **并行** | **每卡一个 git worktree**，`--parallel N`，建议 ≤2 | 多 agent 改同一仓库会互踩；worktree 是干净解法 |
| **冲突** | 收工只拷该卡交付物；路径重叠且内容不同 ⇒ **BLOCKED** | 守住「一个路径一个写者」 |
| **代码规整** | 拆出 `render.py`／`projects.py`／`parallel.py`；`board.py` 仍是 CLI 入口 | 渐进式，不一次性大重构（风险高） |
| **易用性** | 裸 `board` 给面板不给报错；`add` 取代 `new`；`open` 一条命令看板 | 单人工具要少记命令 |

- **未采纳（明确记录）**：一次性把 `board.py` 拆成完整包——风险大于收益，改为按职责渐进拆，每次拆完跑回归。
- 影响面：`tools/` 全部；`AGENTS.md` §2／§3.1；`README`／`docs/usage.md`
- 状态：**已拍板**

## D-004 · 架构期四条待拍板项（**已定** 2026-10-19）

- 日期：2026-10-19
- 依据：用户原话「按照最好最优，人类最轻松，整理废话最少效率最高的方式去用」⇒ 授权发牌席直接裁定，不再逐条请示。

| # | 议题 | **裁定** | 理由 |
|---|---|---|---|
| 1 | **红线②怎么强制**（D1 C-01） | **写权收归看板进程**：agent 只走 `board.py`，人走 `human`＋token；手改 `journal.jsonl` 由 `audit` 检测 | 不违背「文件即卡」；一期只接一个引擎。⛔ 不接受「只检测」——那会让红线②变成口号 |
| 2 | 卡＝目录还是单文件 | **目录**（`card.json` 契约 ＋ `journal.jsonl` 唯一真相 ＋ `lease/`／`artifacts/`／`evidence/`） | 单文件下「历史不可改写」只能靠事后校验 |
| 3 | 是否用 OS 作业对象绑进程树（C-02） | **不用** | 一期不加深平台绑定；**但文档必须写明**「租约挡不住已发生的外部副作用」 |

## D-024 · 租约 epoch 从「日志字段」升为「真栅栏」

- 日期：2026-10-21
- 结论：心跳与提交都支持带 `--epoch`，带了就做**原子 CAS 校验**；orchestrator 自动带上。
- 由来：编排调研（`docs/research/20261021-orchestration-lit/`）对照 Kleppmann 的 fencing token 指出——
  `leases.epoch` 一直在认领时 +1、也写进 claim 事件，但**没有任何写入路径读它**，所以它只是日志，不是栅栏。
  同席位被回收后重新认领（seat 名没变）这一种情况，旧代码拦不住：旧进程照样能心跳、能 submit。
- 落地：
  - `storage.touch_lease(cid, seat, epoch=None)`：带 epoch 时 `UPDATE ... WHERE card_id=? AND seat=? AND epoch=?`，
    rowcount=0 即拒绝（**先读后写不是栅栏**，必须由 SQL 原子判定）。
  - `board.heartbeat(cid, seat, epoch=None)`：换代则 `die`，且心跳事件里记 epoch。
  - `cli.guard_holder(cid, seat, epoch=None)`：epoch 不符直接拒；`submit` 事件记 epoch。
  - `orchestrator`：认领后读取 epoch，心跳线程与提交都带它。
  - `board audit` 增一条：某事件的 epoch 小于该卡已出现过的最大 claim epoch ⇒ 「换代后仍有旧代写入」。
  - `board claim` 打印 epoch，让人/agent 知道该带什么。
- 依据（实测）：`tests/test_lease_race.py::test_epoch_fence` 五条——第一次认领成功／同席位换代认领成功／
  旧代心跳被拒／**对照：当代心跳照常通过**／旧代提交被拒；16 道闸全绿。
- 兼容：`--epoch` 不传时行为与旧版一致（不破坏既有调用方）。
- 未做：CLI 之外的写入路径（如直接调 `storage`）不强制 epoch；旧卡历史事件没有 epoch 字段（不回填）。

## D-025 · 审计的能力边界：事件流被「整体清空」时只能部分发现（2026-10-22 实测）

- 结论：`audit` 能发现「有租约但状态回退」，**发现不了**「把事件清零、连租约一起删」的卡。
- 实测（隔离沙箱，`%TEMP%\opencode\probe-audit2`）：
  1. 建卡 + 认领（3 条事件 + 1 条租约）→ `audit` 干净；
  2. `DELETE FROM events WHERE card_id=?` → `audit` **报错**：`有租约（s1）但状态=待认领 ← 疑似手改状态`；
  3. 若再删租约行，则该卡与「刚建的新卡」**在库内完全无法区分**（cards 表没有 state 列，状态纯由事件推导）。
- 为什么这算边界而不是缺陷：本项目没有独立锚点（cards 表不存事件计数/末条哈希），
  「清空」与「新建」在信息上等价——**不是判据写漏，是缺少独立事实源**。
- 根治形态（未做，列入待办）：`cards` 表加 `events_anchor`（count + last_hash），`append_event` 同步更新，
  `audit` 比对「锚点数 > 实际事件数 ⇒ 事件流被截断」。代价：一次迁移 + 旧卡锚点缺失期（需明示不回填）。
- 已写进 AGENTS §4.1 能力边界，避免对外宣称「audit 能挡住任何改库」。
